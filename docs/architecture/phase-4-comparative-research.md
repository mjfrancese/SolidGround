# Phase 4 comparative research: Groundit and similar projects

This note records research findings from a 2026-09-27 multi-agent review comparing SolidGround with Groundit and a wider set of similar projects, ahead of scoping Phase 4. Every finding went through two independent skeptic verification passes (an evidence lens checking each cited fact, and a fit lens checking whether the proposed idea actually suits SolidGround's constraints and this owner's direction), and a small number of findings that initially came back with placeholder or unusable verification content were re-run until both passes returned real, checkable evidence. This note itself is a further, independent editorial pass over that batch: every citation below was re-verified either against SolidGround's own committed history (`git show HEAD:<path>`) or against the named upstream repository at the commit recorded in Appendix A, and two factual errors that survived the original batch were corrected in the process: the geometry3Sharp commit/date discussion under "What other projects add", and a "no HEIGHT field" reading of USA Structures under "Site-context layers", superseded by the dataset's own peer-reviewed data descriptor and a live FeatureServer query (see below). No `SolidGround.Core`, `SolidGround.Cli`, or `SolidGround.Revit` code was written or changed to produce this note, and no Revit process was launched. It is a research record, not implementation work, and it authorizes no implementation.

## Basis

Eighty-six related repositories, tools, and products were screened; fifteen reports were produced, covering sixteen distinct repositories: the fourteen originally selected for deep-dive (one report saved because Autodesk/civilconnection and its atultegar/CivilConnectionExtended community fork share one report), plus two more distinct repositories — DEM.Net and BlenderGIS — added mid-review to close evidence gaps. That work produced forty findings (F01-F40), each independently checked by both skeptic lenses and each carrying its own `phase4_idea`, effort estimate, and constraint notes. Three lens results (F22 on both lenses; one of the two passes each for F25 and F30) initially returned placeholder content instead of real evidence; all three were re-run and returned real, checkable evidence, and the corrected verdicts are what this note uses throughout, not the discarded placeholders. Two further, narrower live checks fed directly into the findings: a keyless, read-only network check against Groundit's own public elevation-tile source at the public example site measured real tile density against Groundit's own output point count there (feeding the interpolation-ratio finding under "What Groundit does worse"), and two keyless, read-only Overpass API queries at the same site measured real building and road counts and tag completeness (feeding the site-context evidence below). This note's own verification pass re-checked the load-bearing citations directly: SolidGround file:line citations against `git show HEAD:<path>`, and upstream citations against the cloned repository at the commit recorded in Appendix A (in one case, geometry3Sharp's own public commit history, since the local shallow clone carries no history beyond its single checked-out commit).

Only claims a verification pass marked confirmed or corrected are stated as fact below. Where a verdict was "partially confirmed," this note uses the corrected wording, not the original claim; where a verdict was "refuted," this note treats the underlying claim as false and says so.

Baseline: SolidGround's committed history through `ea96afb` (2026-09-27), confirmed as the repository's current `HEAD` at the time of writing. ## Purpose and boundary

This note compares SolidGround's design against Groundit and other similar projects, records real strengths and gaps on both sides, and lays an evidence base for Phase 4 candidates. It does not authorize building any of it. The repository was read-only throughout this review; every citation below is either a repository-relative path with line numbers valid at the baseline commit above, or a named upstream repository and path at the commit recorded in Appendix A.

## Owner decisions (2026-09-27)

**Round 1.**

1. **Coverage.** United States only, 1-meter USGS data, with no coarser or keyless fallback elevation source.
2. **Geometry.** New context or boundary geometry goes into the host model, not a separate linked site model.
3. **User profile.** A single, non-commercial user who wants "the most versatile (but still accurate as hell) tool possible."
4. **Revit version.** Revit 2027 and later only; no multi-version support.

**Round 2.**

(a) **Site-context layers ("Full context epic").** Plan buildings, with heights, plus roads as their own large epic, comparable in size to Phase 3. This note's "Site-context layers" section below is the evidence base for that epic; it does not scope or authorize it.

(b) **Guaranteed worst-case vertical error ("Measure first").** Ship the achieved worst-case/RMS vertical-error diagnostic described under Phase 4 candidates first; decide between the two `SimplificationMethod.TinError` implementations (a hand-built, exact-sample-preserving greedy TIN vs. geometry3Sharp's QEM) only after that diagnostic produces real numbers on the shipping simplifier's own output.

(c) **Issue #18 (classified ground-return point-cloud source): "Yes, investigate."** This authorizes an investigation-first track only: verify current EPT/COPC access over USGS's own public bucket, evaluate fully managed decoding options, and report back. It does not authorize any implementation; Issue #18's own acceptance criteria already state that no implementation begins without a separate, owner-approved scope decision, and this round-2 decision does not change that gate. As of this note, Issue #18's GitHub labels (`status: blocked`, `future`) have not yet been updated to reflect this decision; that update is part of the next step below, not this note.

(d) **Next step.** Commit this note to `docs/architecture`, then prepare a Phase 4 milestone and draft issues for owner review, before anything is published to GitHub. This mirrors how Phase 3's own research note and draft-issues file were sequenced.

**Still open.** See "Open owner questions" below for the three questions this round of decisions deliberately left open.

## Summary

SolidGround already leads on the things that matter most for an accuracy-first, single-user tool: transaction safety and rollback discipline, vertical-datum and unit rigor, architecture-boundary enforcement, and an interactive dialog that is more disciplined about error reporting than any comparator reviewed. Groundit is the one project close enough in scope to be a real yardstick, and it is ahead only on a handful of specific, cheap-to-copy-the-idea-of conveniences (live pre-fetch estimates, a CRS convergence/scale-factor readout, a working progress bar during real downloads), while carrying real, confirmed defects of its own: an undocumented, unlabeled interpolation ratio roughly three orders of magnitude above its real measured density at the public example site, no vertical-datum declaration anywhere in its repository, and a confirmed nested-transaction bug in its own "Update Site" flow that Revit's own API forbids (found by static code reading against documented Revit API contracts, not an observed runtime failure — neither this review nor its source material launched a live Revit process against Groundit). Ranked by accuracy and model-integrity impact first, versatility for this owner second, and effort last, the strongest Phase 4 candidates run from small to substantial: two model-integrity guardrails that close silent-failure classes in the transaction path already built; a newly-confirmed-feasible diagnostic that would measure, rather than merely approximate, the existing simplifier's real vertical error, feeding the larger and still-open decision of whether to build a certified-error-bound TIN method; a handful of small, additive CRS/geolocation and provenance-completeness items; and a grouped set of cheap dialog-polish conveniences, kept last on purpose since cheapness is not the same as importance to this owner. Site-context layers (buildings, roads) are now approved as their own future epic, comparable in size to Phase 3; this note assembles the evidence base for that epic but does not scope or build it. A second, separate track — Issue #18, a classified ground-return point-cloud source — is now an approved investigation, not yet a build item.

## What Groundit is

Groundit is a pyRevit/IronPython Revit add-in. An operator draws an area of interest in an ordinary web browser — a Leaflet map bridged to Revit through a local HTTP server, not an embedded browser control (a "bridge, don't embed" design its own README states explicitly rejects WebView2 for the same native-binary reason SolidGround's own rules would forbid it, F14). Groundit then fetches global, keyless AWS elevation tiles (Terrarium-encoded PNGs, roughly 30 m worldwide and finer over parts of the US), builds terrain — and, optionally, OSM-derived buildings and roads — into a brand-new background Revit document, saves it, and links it into the host model, deliberately keeping the host document free of thousands of context elements and inheriting Revit's own workset/phase/view-override preservation on link reload (F13, F33).

A live, keyless, read-only network check against Groundit's own elevation source at the public example site (part of this review's own evidence-gathering, not a code change) found two things Groundit never surfaces to its own user. First, at Groundit's default settings only a handful of real elevation-tile pixels (6) fall inside a site-sized box, yet its fixed grid-sizing formula still produces roughly 1,650 times that many output points there, all bilinearly interpolated, with nothing in the output distinguishing measured density from manufactured density (F31). Second, the site's real underlying elevation data traces to a single USGS source tile with an acquisition year around 2008; Groundit's network layer discards HTTP headers on every transport and so never reads or surfaces this, and its repository never declares which vertical datum any of its elevation values are referenced to in the first place (F35).

## What Groundit does better than SolidGround

- **Grid convergence and point scale factor, computed and shown.** Groundit derives both by numerical differentiation of its own projection and displays them live; it also lets an operator choose true-north vs. grid-north alignment. SolidGround computes and shows neither today (F08).
- **Live, offline pre-fetch sizing.** Groundit's picker shows real-time area size, point count, tile count, ground-sample distance, and warnings the instant a drawn box or budget changes, all before any network call. SolidGround's dialog has no equivalent signal between choosing a buffer/budget and spending a real request (F10).
- **A real, cancellable progress bar for genuine network calls**, achieved by chunking the download and checkpointing between chunks (`Groundit.tab/Site.panel/Import Site.pushbutton/script.py:110-124`; `lib/groundit/source.py:55-90`, `fetch_terrain`) — proof that synchronous, in-process code does not inherently preclude live progress. SolidGround's dialog blocks the UI thread for one atomic call with no way to checkpoint it today (F37).
- **A reachability preflight probe** run before its long unattended browser session opens, with cause-distinguishing error text, plus automatic retry with transport fallback for transient failures. SolidGround has neither (F29).
- **A saved-request sidecar** that lets its "Update Site" repick flow reopen pre-filled from a prior run. SolidGround's comparable, richer provenance record is not yet wired that far (F23).
- **Anchoring one coordinate-transform test to officially published, external third-party worked examples** (national mapping-agency reference values), rather than only to same-repository or same-engine values. A good testing pattern SolidGround's own equivalent test doesn't yet fully match, for an already-documented reason (no PROJ/pyproj installation was available when that fixture was last re-verified) (F26).

## What Groundit does worse than SolidGround

- **A confirmed nested-transaction bug in its own "Update Site" flow** (found by static code reading against documented Revit API contracts, not an observed runtime failure — neither this review nor its source material launched a live Revit process against Groundit). It opens a Transaction on the host document, then tries to unload/rebuild/save/reload a separate linked document — an operation Revit's own API documents as forbidden while any transaction is open elsewhere — and the resulting exception is silently swallowed, disabling Groundit's own reload-on-failure safety net (F34).
- **A severity-blind failure handler.** Its warning preprocessor always continues and always deletes every warning regardless of severity; SolidGround's preprocessor inspects severity and forces rollback on any Error/DocumentCorruption message before deleting anything (F34).
- **Silently substitutes true sea level (0.0 m) for any elevation-tile pixel whose fetch failed, with no counter or warning anywhere.** Every per-tile fetch is wrapped in a bare `try`/`except: continue` (`lib/groundit/source.py:69-78`), and the mosaic returns the literal float `0.0` for any pixel whose tile never loaded (`lib/groundit/tiles.py:262-270`); the pipeline only raises when the total tile count is zero (`source.py:80-83`), so a partial failure is never surfaced. This is the single worst data-fidelity defect found in this review's acquisition-dimension comparison. It is independently corroborated by the unrelated `louis-e/arnis` project's USGS 3DEP tile provider, which counts and logs every tile failure, attempts a same-run fallback to a coarser public source, and NaN-fills only what remains missing after that (`src/elevation/providers/fixed_tile.rs:562-575, 587-613, 623-626`) — real, running code independently converging on "count and report every failure, never let a hole become a real elevation." SolidGround's own equivalent path already avoids this defect by construction: `AaiGridParser.Parse` converts any cell equal to the header's `NoDataValue` to `null` before it can become a `double` (`src/SolidGround.Core/Rasters/AaiGridParser.cs:52`), and every downstream stage stores cells as nullable throughout clipping and simplification.
- **No vertical-datum declaration anywhere in the repository**, and elevation vintage metadata it never reads because its network layer discards HTTP headers. SolidGround already declares NAVD88 explicitly, sourced from published documentation and scoped to the CONUS UTM zones where it actually applies, declining Alaska/Hawaii/Puerto Rico/the territories rather than guessing (F35).
- **Silently fabricates points to hit a size target.** No comparable behavior exists in SolidGround, which only ever decimates real cells and is structurally guaranteed, by a constructor check, never to return more points than it was given (F31).
- **Hardcodes the international foot (0.3048 m exactly) for every value, including elevation**, a real ~2 parts-per-million discrepancy for US survey-foot workflows that SolidGround avoids by modeling both units explicitly (F36).
- **Shows raw, longer error text directly in a user-facing alert**, and its own transport-error list is itself silently truncated to the last four attempts with nothing persisted to disk — arguably a worse gap than "unbounded," just a quieter one. SolidGround has a fixed inline cap plus a complete report always written to a named log file (F37).
- **Its README asserts an automated cross-check between its JavaScript estimate and its Python engine that does not actually exist anywhere in the repository.** The real mechanism is a hand-maintained code comment, and a concrete constant defined independently in two files has no test protecting it from drifting apart (F38).
- **Its own architecture-boundary check is a weaker, runtime-only import sweep**, which would miss a Revit reference sitting in code that is never executed during the sweep. SolidGround's equivalent test reflects over compiled IL and would catch it regardless (F38).

## What other projects add

Eighty-six related repositories, tools, and products were screened; fifteen were deep-dived for this comparison. None is copied from; each entry below is a pattern or cautionary lesson, per this project's own licensing rules.

- **GIS2BIM** (Dynamo node library): accesses Revit's shared-coordinates parameters by display-name string with an undocumented unit-scale factor, fragile compared to SolidGround's typed mechanism (F32). Its `TextNote`-on-import pattern for labeling a parcel is worth borrowing as an idea (F25).
- **mantleplace-dcc** (Apache-2.0, source-only, no Revit release published yet, targeting Revit 2025/2026/2027 plus Unreal): the only comparator that both builds terrain into the host document (matching SolidGround's and the owner's own choice, F33) and implements a working reuse/refuse/create identity guard for repeated imports, though its own multi-match case silently keeps the first match rather than refusing, a pitfall to avoid (F01). Also writes Revit's `SiteLocation` from the same geocoded origin used for shared coordinates (F21).
- **KartverketToposolid**: embeds a live map via WebView2 plus Leaflet inside Revit, confirmed blocked for SolidGround under its own native-binary rule (F14). Zero automated tests or CI. Its own code admits the shared-coordinates parameter values and the actual base-point position "can differ," with nothing that checks (F32).
- **CivilConnection / CivilConnectionExtended** (official Civil 3D-Revit bridge, and a community fork): assumes a user's own prior "Acquire Coordinates" step with no independent CRS capture at all; has no transaction-scoped atomic update, rollback, or post-creation verification (F34); a real unguarded null dereference in its point-based family-instance lookup is inherited unchanged by the fork (F01). Requires a live licensed Civil 3D session, so it has never had CI (F28).
- **Gismo** (Grasshopper/GhPython): its per-input docstring convention gives every component a free, native hover tooltip and links a step-by-step key-acquisition tutorial right at the key input, a real UX gap SolidGround's own dialog and docs still have (F24, F25).
- **Heron** (Rhino/Grasshopper GIS plugin): the most complete implementation of OSM's "Simple 3D Buildings" tagging found (building parts, roof shapes) among the OSM-consuming comparators, but its own height fallback carries no measured-vs-default flag, and it depends on a third-party LAZ codec fork with a confirmed, still-unfixed decompression bug in exactly the channel a classified point cloud would need (F39, F18).
- **ifc-site** (pure Python/Docker IFC service, no host BIM application at all): substitutes a batch mean or a hardcoded value for any failed per-point elevation lookup, with only a console warning and no per-vertex flag in its output, exactly the class of bug SolidGround's own NODATA rule already forbids for terrain (F16).
- **geometry3Sharp** (BSL-1.0, mature managed mesh-simplification library): its own unrelated default (preserve boundary shape) independently validates SolidGround's structural-retention design. Its simplifier (`mesh/Reducer.cs`) last received a functional change in commit `b714edfb` (2018-06-20, "improve FastCollapsePass"); the repository's own later commits are README-only, including one that explicitly points users at successor forks — a stronger, more current staleness signal than either of this review's own earlier passes reported (F07).
- **delatin** (ISC-licensed, a compact greedy-insertion TIN refiner — `index.js` alone is 477 lines, confirmed by direct count): gives a certified worst-case vertical-error bound and never blends a point, but its geometry predicates are non-robust and its bootstrap is unsafe for NODATA-holed grids, a real design reference, not a library to depend on directly (F07).
- **geotiff.net** (MIT, managed C#): the only comparator with a genuine cross-implementation conformance methodology (diffing against the real `geotiff.js` library), but its own CRS/GeoKey layer is untested and marked Experimental, an open, maintainer-acknowledged gap (F27).
- **laszip.net** (LGPL-2.1) and its actively-maintained fork: the only from-scratch managed LAZ codec found; has three real, confirmed bugs in LAS 1.4 classification/RGB+NIR decompression, one still unfixed in the exact production fork Heron depends on (F18).
- **goto.archi Topography** (closed-source, commercial): documents both classification-2 ground-point emphasis and manual "high-density zones" for spatially targeted extra density, real evidence of market demand for both, with no disclosed automatic terrain-aware algorithm for either (F18, F20).
- **Equator Studios Topography** (closed-source, hosted SaaS, not a Revit add-in): no disclosed internals; included for completeness only.
- **DEM.Net** (open-source .NET elevation library, no US 1 m/3DEP coverage): independently repeats the "0.0 as missing data" sentinel bug in multiple places and hardcodes a NODATA constant that matches none of its own eleven registered datasets' own declared sentinels (F30).
- **BlenderGIS** (Blender/Python importer): silently fills a failed terrain-drape lookup with a fabricated mean, and silently randomizes a building-height default with no flag, both real anti-patterns SolidGround's own NODATA discipline already avoids for terrain and should extend if it ever adds context layers (F12, F16, F39).

## Site-context layers

No building/road/context-layer code exists in SolidGround today. The owner has now approved planning buildings (with heights) and roads as their own future epic, comparable in size to Phase 3; this section is the evidence base for that epic, not a design or a build.

**The licensing risk is real, and conditional, not theoretical.** If SolidGround ever placed OSM-derived (or Microsoft- or Overture-sourced, both of which include OSM data) building or road vertex geometry directly into the host model as measurable elements — the way Groundit, Heron, and BlenderGIS all do — that geometry plausibly counts as an ODbL "Derivative Database" under the OpenStreetMap Foundation's own Attribution Guideline ("If a Produced Work is used to extract, copy, or recreate substantial parts of the OpenStreetMap data, it is considered to be a Derivative Database," `osmfoundation.org/wiki/Licence/Attribution_Guidelines`), because the element's vertices are exact, re-extractable coordinates, not a redigitized approximation. That classification is necessary but not sufficient to trigger ODbL's share-alike obligation: under ODbL 1.0 itself, that duty attaches only once the derivative is "Publicly Use[d]" (section 4.4), and section 4.5(c) carves out purely internal use. Given this owner's own stated audience — "just me, not commercial at all" — a private, never-public reading is available in principle. In practice it is fragile for this project specifically: the repository is public and its own conventions favor committing small deterministic fixtures and narrating detailed evidence in public issues and pull requests, either of which would likely count as public use of any OSM-derived geometry (F11). None of the six Revit- or BIM-adjacent projects examined for this dimension (Groundit, mantleplace-dcc, GIS2BIM, ifc-site, BlenderGIS, Heron) discharges attribution or share-alike for OSM-derived building or road data today; Groundit's own README advises attribution but enforces nothing in the model, sidecar, or run report.

**This conflicts with an existing AGENTS.md sentence unless the owner amends it.** Groundit's own data sources are AWS's keyless global elevation tiles and OpenStreetMap via Overpass. `AGENTS.md` states plainly, in its "Groundit is an architecture reference only" paragraph, that "the agent must not copy its... data-source... design." A context epic that used OSM/Overpass as its building or road source would be adopting the identical category of data source AGENTS.md's own sentence names, not merely a similar idea; it would need an explicit, owner-accepted AGENTS.md amendment before that source could be used, following the same pattern Phase 3 used for its own boundary sentence: direct owner acceptance of a proposal document (`docs/planning/phase-3-draft-issues.md`), committed with reference to the Phase 3 epic (`#26`, `type: epic`) rather than a dedicated `type: gate` issue (commit `d7af89e`, "Add the accepted Phase 3 boundary sentence to AGENTS.md"). The one `type: gate` issue actually tied to Phase 3 AGENTS.md/conventions amendments, `#34`, remains open (`status: blocked`) as of this note's own baseline. Using a US federal source instead avoids the conflict entirely, without needing an amendment for the source choice itself.

**US source options for buildings.** USA Structures (FEMA/ORNL/USGS) is CC BY 4.0, attribution-only, no share-alike, confirmed directly against the dataset's own hosted ArcGIS item page (`licenseInfo`: "This work is licensed under a Creative Commons by Attribution (CC BY 4.0) license," `arcgis.com/sharing/rest/content/items/0ec8512ad21e4bb987d7e848d14e7e24`, retrieved 2026-09-27), and is servable through a live, public, GeoJSON-capable ArcGIS FeatureServer (`services2.arcgis.com/.../USA_Structures_View/FeatureServer/0`, `access: public`, no key required), the same kind of ingestion SolidGround already uses for county parcels. Its published schema does carry a real `HEIGHT` field (meters), correcting an earlier reading of this same dataset that reported no height field at all — but the correction is not total: the dataset's own peer-reviewed data descriptor states `HEIGHT` is populated only for structures sourced from one in-house NGA 133-city lidar layer, not nationwide, which a direct live query of the FeatureServer confirmed empirically (populated, plausible values only on records sourced from that layer; null elsewhere). Footprint and orientation, not height, are the realistic first use of this dataset almost everywhere (F11).

**US source options for roads.** US Census TIGER/Line road centerlines are public domain (a US government work) and avoid ODbL entirely, the same status as USA Structures. They carry no width or lane-count attributes, the same sparse-attribute tradeoff USA Structures has for height. The USGS National Transportation Dataset is a plausible second option this review did not independently examine; its licensing terms and whether it carries road-width data should be verified before it is relied on for anything.

**Height is a separate, harder problem, linked to Issue #18.** OSM height tags are present on under 20% of US buildings nationally (a widely cited figure, not one single citable study); a live sample at the public example site was consistent with this (0 of 8 buildings had a height or `building:height` tag; 5 of 8 had a `building:levels` tag). Every OSM-tag-consuming importer examined falls back to a guessed default when a tag is missing, and only Groundit flags which source (measured, levels-derived, or defaulted) produced each building's height. The accurate answer is deriving height from the same USGS 3DEP lidar program the terrain pipeline already depends on: the classified point cloud's own building-class returns, differenced against the bare-earth surface SolidGround already fetches. This technique is already proven at national scale (Meta/Overture Maps Foundation, 2023), and it is exactly the future classified point-cloud source `AGENTS.md`'s own "Architecture" section already anticipates (`AGENTS.md:20`). It is gated behind Issue #18, now an approved investigation track (see Owner decisions, Round 2c) but not yet a build item: the one candidate fully-managed LAZ codec found in this whole search has a real, unfixed bug in exactly the classification/RGB+NIR channel a ground-return height computation would need, and its genuinely usable LAS 1.4/LAZ support lives only on an unreleased branch (F12, F18).

**Host-model design constraints, if this is ever built.** The owner's host-model-only direction (Round 1, item 2) rules out Groundit's own approach, which links a separate document specifically to keep "thousands of context elements" out of the host and inherit workset/phase/view-override preservation from Revit's own link-reload mechanism. mantleplace-dcc is the only precedent found that actually builds context elements into the active host document: buildings as `DirectShape` in `OST_GenericModel` (matching Groundit's own independent choice, but for an unrelated reason: Groundit's own comment cites `OST_Mass`'s hidden-by-default visibility (`lib/groundit/build.py:62-63`), while mantleplace-dcc's own doc comment gives a different rationale entirely — matching Autodesk Forma's own convention for context geometry, plus avoiding an outright DirectShape-creation failure (`revit/src/MantlePlace.Revit.Addin/RevitBundleImporter.SiteVectors.cs:76-78`) — so the two projects converge on the same category, not the same stated reason), chunked at 200 elements per transaction so Cancel is honored and Revit repaints between commits, each element stamped with an identity string so a repeated import creates only what a prior cancel left missing, and trees as native `Planting`-category `FamilyInstance`s once a clean native match exists, falling back to `DirectShape` only when a family fails to load. Even this precedent assigns no Revit workset to anything it creates — a real, unsolved design gap in every host-model precedent examined, not a solved problem to copy. A context epic would also need its own reuse/refuse/create identity guard (generalizing the guard proposed under Phase 4 candidates for the toposolid path itself), the existing NODATA discipline extended explicitly to cover a failed per-point drape or lookup (two of three non-Groundit implementations examined fabricate a plausible-looking value on exactly this kind of failure, F16), and a pre-fetch size guard: a live, keyless Overpass sample at the public example site, at a 300 m radius, returned 522 highway-way elements against only 8 building elements, with per-feature size tags (width, lanes) nearly absent (F15). No embedded map is available: a WebView2-based picker is blocked by two independent `AGENTS.md` rules (the general ban on native binaries in the Revit process, and the isolated add-in context's managed-only dependency rule), not merely one (F14). A compliant alternative, if a visual preview is ever wanted, is a from-scratch, code-behind-only WPF rendering of geometry `SolidGround.Core` already resolves, with no basemap imagery.

This evidence base supports scoping the approved context epic; it does not itself scope, design, or authorize any implementation. The likely first cut, on this evidence, is footprints-only via USA Structures, with building massing and height deferred to a later decision that depends on Issue #18's own investigation.

## Phase 4 candidates

Ranked for this owner by accuracy and model-integrity impact first, versatility second, and effort last. Small, cheap polish items are grouped near the bottom on purpose; cheapness is not the same as importance to an owner whose bar is "the most versatile (but still accurate as hell)."

- **Manually-drawn high-density zones within the existing point budget** — one commercial vendor (goto.archi) ships this manually, which shows vendor conviction that spatially-targeted density control is worth building, though the cited evidence does not establish independent end-user demand (no usage methodology is published). Python never becomes a SolidGround dependency (F26).
- **An independent cross-check for GeoTIFF GeoKey parsing** — the specific plan first proposed (a one-time external note against a fixture that doesn't exist) needs rework; the better version is a small, permanent, hand-coded independent parser test reusing bytes the test suite already builds, matching the same pattern SolidGround already uses for its own coordinate-transform cross-check (F27).

## Open owner questions

1. **CRS-identity and geolocation writes.** Should SolidGround write a CRS-identity tag and/or the geocoded latitude/longitude/time zone into the model automatically, as an opt-in gated the same way shared coordinates are today? Two corrections narrow this question versus how it was first framed. First, API visibility, settled by a direct metadata read of the installed Revit 2027 `RevitAPI.dll` (27.0.10.13): `SiteLocation.SetGeoCoordinateSystem(string)`, the read-only `SiteLocation.GeoCoordinateSystemId` and `GeoCoordinateSystemDefinition` properties, and `SiteLocation.Latitude`/`TimeZone` are public, but `SiteLocation.GetEPSGCode()` and `ProjectLocation.SetProjectedSpaceToLocalTrf` (six parameters) are compiled with assembly-only (`internal`) visibility despite appearing in `RevitAPI.xml`. An add-in can therefore write a CRS identity and read it back through `GeoCoordinateSystemId`, but cannot set a combined scale factor through this API. Separately, the geolocation write is not "already resolved and sitting ready" as first assumed: the interactive dialog resolves a real geocoded point, but today's data flow discards its raw latitude/longitude before it reaches the transaction, keeping only a derived parcel polygon and non-coordinate text — so a `SiteLocation` write would need either new plumbing to carry the literal geocode point that far, or would use a parcel centroid instead, which is not the same point.
2. **Acquisition disk cache.** Is a disk-backed cache for repeated same-area OpenTopography fetches worth building? The historical cost is real but smaller than first stated: this project's own record shows two, not three, deliberate live re-fetches of the public example site, and the CLI already has a manual fetch-once/process-many workaround for its own workflow. The clearest remaining pain point is narrower: `SolidGround.Revit`'s settings-driven fetch/process switch today requires hand-editing a machine-wide JSON settings file to reuse a prior download, where the CLI needs only a flag.
3. **Unattended Revit-hosted testing.** Should the standing "no live-driving harness" debugging convention ever be revisited to allow a local, never-in-CI Revit journal-replay smoke test, or should the current dated manual-evidence-session discipline remain the only verification method? One correction to the evidence for this question: Revit's own journal-cooperation surface (`ExternalCommandData.JournalData`, `ControlledApplication.IsJournalPlaying`, and related members) is well documented in the installed Revit 2027 SDK reference — it is not, as first reported, undocumented. What remains genuinely unverified is only the external, command-line mechanism for launching Revit against a journal file from outside the process for orchestration.
