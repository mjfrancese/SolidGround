# Phase 1 validation at the reference parcel

Issue #10 validates the Phase 1 pipeline end to end against a real OpenTopography acquisition and a captured raster from the reference parcel scenario, and separately reproduces and fixes a clean-checkout determinism defect that only a fresh clone (not a workstation with a warm build) could expose. It adds no package reference: every step below runs entirely inside `dotnet restore`/`build`/`test`, the shipped `process`/`fetch`/`run`/`verify` CLI commands, and one small, uncommitted, single-purpose grid-statistics console program used only to compute descriptive terrain numbers from the raster this validation captured; that program and the raster it analyzed are not part of the repository (see "Known limitations and follow-ups").

## Response packaging and metadata observed

A direct capture of the same 120 m box outside the CLI recorded exactly what OpenTopography returns. The `AAIGrid` request (`outputFormat=AAIGrid`) returned HTTP 200, `Content-Type: application/octet-stream`, a `Content-Disposition: attachment` header naming a `.asc` file, chunked transfer with no `Content-Length`, 290,474 bytes, LF line endings throughout, and a six-line header with no CRS, datum, or unit declaration of any kind:

```
ncols        124
nrows        117
xllcorner    [withheld]
yllcorner    [withheld]
cellsize     1.000000000000
NODATA_value  -999999
```

A `GTiff` request for the identical box returned HTTP 200, 46,056 bytes, little-endian TIFF with 18 IFD tags: `ImageWidth` 124, `ImageLength` 117, `BitsPerSample` 32, `SampleFormat` 3 (IEEE float), `Compression` 8 (Deflate), `Predictor` 1 (none), one 512×512 tile, `ModelPixelScale` (1, 1, 0), `ModelTiepoint` (0, 0, 0 → [withheld], [withheld], 0), and `GDAL_NODATA "-999999"` with no `GDAL_METADATA` tag. Its GeoKeys carry `GTModelTypeGeoKey` 1 (projected), `GTRasterTypeGeoKey` 1 (PixelIsArea), `GTCitationGeoKey` "NAD83 / UTM zone 15N", `GeogCitationGeoKey` "NAD83", `ProjectedCSTypeGeoKey` 26915, and `ProjLinearUnitsGeoKey` 9001 (metre), but no vertical GeoKeys (4096–4099) at all; `GTRasterTypeGeoKey`'s `PixelIsArea` value is what licenses reading `ModelTiepoint` as the outer corner of the upper-left pixel — matching `yllcorner + nrows * cellsize` — rather than that pixel's center, the interpretation the same tiepoint bytes would carry under `PixelIsPoint`. Width, height, the tiepoint (`yllcorner + nrows * cellsize = [withheld]`), pixel scale, and NODATA value all agree exactly between the two response shapes for the same request.

The [OpenTopography OpenAPI definition](https://portal.opentopography.org/apidocs/openapi.json) documents `/API/usgsdem`'s `outputFormat` enum as `GTiff`/`AAIGrid`/`HFA` (default `GTiff`) and its response codes as 200/204/400/401/500, but says nothing about output projection, sidecar files, or a minimum request area. The [USGS 1 meter DEM dataset page](https://portal.opentopography.org/raster?opentopoID=OTNED.012021.4269.3) states: "The spatial reference used for tiles of the one-meter DEM within the conterminous United States (CONUS) is Universal Transverse Mercator (UTM) in units of meters, and in conformance with the North American Datum of 1983 (NAD83)," "Data is distributed in the UTM Zone in which it lies," and "All bare earth elevation values are in meters and are referenced to the North American Vertical Datum of 1988 (NAVD88)." [OpenTopography's developer documentation](https://opentopography.org/developers) states rate limits of 200 calls/24h for academic keys and 50/24h otherwise.

This observed packaging matches the first of the two cases the "Fail rather than assume" metadata policy in `docs/architecture/opentopography-usgs1m-source.md` already anticipated and handled — bare text, which fails, versus a zip with a `.prj` or `.aux.xml` sidecar, which succeeds — confirming that anticipated failure mode live rather than revealing an unanticipated third shape, which is exactly why `OpenTopographyUsgs1mSource` throws `OpenTopographySourceMetadataException` rather than guessing a CRS from the dataset's own documentation. The same note's "Contract adjustment (deliverable A)" section already states that `collectionPeriod` and `qualityLevel` are always `null` for this source, because the `usgsdem` endpoint reports neither; that held throughout every run in this validation.

## Terrain quality observed under canopy

A hand-written, uncommitted grid-statistics program computed descriptive terrain statistics directly from the captured 124×117 raster (14,508 cells), using the same formulas throughout: elevation min/max/mean/median over valid cells only; a local residual `r(cell) = |z - mean(valid orthogonal neighbors)|` computed only where at least 3 of the up-to-4 neighbors are valid; slope in degrees from central differences (`atan(sqrt(gx² + gy²)) * 180/π`) where all four orthogonal neighbors are valid; and a flat-run proxy counting maximal runs of 5 or more positionally adjacent, identically valued cells along a row or column.

- NODATA: 0 of 14,508 cells (0%).
- Elevation: min 171.824432, max 176.514359, mean 173.951560, median 173.518600 m; 14,015 distinct values; smallest positive gap between distinct values 0.000015 m.
- Local residual (14,504 qualifying cells): mean 0.007159, p50 0.004971, p90 0.015675, p99 0.036491, max 0.189392 m; fraction with `r > 0.10` m: 0.000207 (3 cells); fraction with `r > 0.25` or `r > 0.50` m: 0.
- Slope (14,030 qualifying cells): mean 3.195°, p90 6.186°, max 21.795°.
- Flat runs of 5 or more identical consecutive values: 0 runs, longest 0, fraction 0.
- Mean residual by thirds: rows top 0.006244, middle 0.007323, bottom 0.007909; columns left 0.006176, middle 0.007758, right 0.007533 m.

The honest interpretation: this box is a smooth, fully populated surface at 1 m spacing, with no NODATA holes and no flat interpolation runs, and a neighbor residual that is millimeter-scale almost everywhere. Sparse ground returns under mature canopy show up here as interpolated smoothness, not as gaps or noise — the three cells above 0.10 m residual and the 21.8° maximum slope are localized breaks (curb, wall, artifact) whose cause cannot be told from the DEM alone. Smoothness is not accuracy: every residual and slope figure above is a **same-surface proxy** describing how consistent the DEM is with its own neighboring cells, not a measurement of the distance between this surface and the true ground beneath the trees, and it must never be read as an RMSE or accuracy figure. The [Scope](../../README.md#scope) section's expectation of visible interpolation roughness was not borne out at 1 m resolution: the observed surface hides sparse returns behind smoothness rather than revealing them as gaps.

## NODATA behavior observed

The captured 120 m box contained zero NODATA cells (0 of 14,508), so every offline `process` run's sentinel-handling path was exercised on a grid with nothing to remove, and the parcel-clip run (P5) reported 0 source-NODATA cells inside the clipped region as well. What this validation did not observe is a live raster that actually contains NODATA holes (for example, near the edge of a collection project or a data void): that path remains covered only by the offline/fixture test suite's own synthetic grids, not by a real OpenTopography response captured in this session.

## Point reduction observed

The whole-grid run (P1) did not use its full 15,000-point budget: 13,094 of 14,508 candidates were retained, 1,906 points of budget unused. The three-pass allocation explains the gap exactly. After 478 structural (edge) points, the remaining budget of 14,522 splits into a curvature allotment of 11,618 (80%) and a coverage reserve of 2,904 (the default 20% coverage-floor fraction); Pass 2 took its entire curvature allotment (11,618 candidates were selected by curvature rank), leaving Pass 3's coverage-floor budget at the full 2,904. But Pass 3 selects at most one point per spatial block regardless of how many unselected candidates a block holds, and the roughly 2,412 remaining candidates grouped into only 998 distinct non-empty blocks — so only 998 of the 2,904-point coverage reserve were actually used, and 1,414 low-curvature interior cells were never retained even though the overall budget was not reached. See "Three-pass budget allocation" in `docs/architecture/terrain-aware-decimation.md` for the exact allocation rule and the block-based coverage-floor mechanism that produces this outcome.

At an artificially tight budget of 2,000 over the 60 m-radius clip (P3 vs. P4), curvature-aware retention discarded candidates with removed-candidate curvature up to 0.0614 (mean 0.0243) and elevation residual up to 0.0153 m (mean 0.0049 m), while uniform sampling at the identical budget discarded candidates with curvature up to 0.3174 (mean 0.0319) and residual up to 0.1396 m (mean 0.0072 m) — uniform sampling discards markedly sharper terrain features than curvature-aware selection keeps at the same point count.

Every run printed its coverage-floor fraction (`0.2` in every case above) to the console, but that value is never recorded in the export document itself — `provenance.simplification` serializes only the point budget and method name. This is a pre-existing, documented gap; see "Known limitations and follow-ups" in `docs/architecture/cli-workflow.md` and "Known limitations" in `docs/architecture/provenance-and-deterministic-exports.md`.

## Accuracy statement

Nothing observed in this validation changes AGENTS.md's product claims, and this note restates them rather than replacing them: SolidGround is a site-form tool, not a survey instrument. QL2 bare-earth lidar is roughly 10 cm vertical RMSE under favorable conditions and worse under mature canopy such as the reference parcel fixture, and the resulting surface remains unsuitable for foundation-perimeter grading or construction layout — those tasks need field measurement or a professional survey. Every roughness, residual, and slope figure reported above (and everywhere in this note) is a same-surface proxy computed from a DEM's own neighboring cells, not an accuracy or RMSE figure; a smooth, fully populated 1 m surface under canopy is consistent with either a well-observed surface or a heavily interpolated one, and this validation's statistics cannot distinguish between them.

## Source packaging decision for the owner

The live capture surfaces a direct conflict with AGENTS.md's "Data and numeric contracts" requirement to read and preserve the actual raster coordinate reference system and vertical metadata returned for each request: the observed bare `AAIGrid` response carries no reference metadata at all, and the same request's `GTiff` response carries a horizontal reference (`EPSG:26915`) but no vertical reference. The vertical reference can therefore only come from the dataset's own published documentation, and must be labelled as declared, not carried, under any of the following options — which is itself an AGENTS.md amendment for the owner to make.

1. **Hybrid metadata request (recommended).** Keep `AAIGrid` for the elevation data; add a second `GTiff` request over the same box and parse only its TIFF IFD and GeoKey directory in managed code (no pixel decoding or decompression) for the projected/geographic CRS, citations, linear unit, tiepoint, pixel scale, dimensions, and NODATA value. Require exact agreement with the `AAIGrid` header or fail with `OpenTopographySourceMetadataException`. Cost: a second HTTP call per acquisition against the daily quota (50 non-academic, 200 academic accounts) and roughly a few hundred lines of new parsing code with tests; it keeps the existing `AAIGrid` contract intact.
2. **`GTiff` only.** A single request, but it requires a managed GeoTIFF reader handling tiled or stripped data, Deflate decompression, an unguaranteed predictor setting, 32-bit float samples, and `GDAL_NODATA`; more code and more exposure to a server-side format change, and it changes the AGENTS.md sentence that currently mandates `AAIGrid`.
3. **Documented-zone inference.** Derive the NAD83 UTM zone from the AOI's own longitude and validate the header ranges, with no extra request — but this assumes the projection instead of reading it, which AGENTS.md forbids outright, and it is fragile near a zone boundary (the owner's reference parcel happened to sit close to the zone 15/16 boundary, a coincidence of its real, withheld location, not a deliberate test design).

Option 1 is recommended, together with a minimum-area padding follow-up: pad the fetch envelope to at least a 120 m square (the smallest size observed to be accepted; 100 m was rejected) while still clipping the result to the actual parcel, record the padding applied in provenance, and give the unpadded parcel path a clear report of the source's own minimum-area rejection rather than a generic usage error. The decision among these options is the owner's to record on Issue #10, not this note's to make.

## Known limitations and follow-ups

- **No Core roughness statistic.** The residual, slope, and flat-run statistics in "Terrain quality observed under canopy" come from a standalone scratch program, not from any `SolidGround.Core` type; Core has no equivalent built-in diagnostic today.
- **The coverage floor is still not recorded in the export document**, as already tracked in `docs/architecture/cli-workflow.md`'s "Known limitations and follow-ups" and `docs/architecture/provenance-and-deterministic-exports.md`'s "Known limitations".
- **The parcel fixture is synthetic.** `example-site-synthetic-parcel.geojson` is a nominal [withheld] footprint, not a surveyed boundary; every parcel-clip number above (P5) inherits that approximation.
- **The captured raster and the grid-statistics program are not committed.** The raster is downloaded bulk data, which AGENTS.md's "Secrets, downloads, and logs" section says is ignored by default; the statistics program was a throwaway, single-purpose scratch tool, not a reviewed addition to the repository.
- **The minimum request area remains undocumented by OpenTopography.** This validation only bracketed it empirically (100 m rejected, 120 m accepted) for one location; the true floor, and whether it varies by location, is unconfirmed. **Update, Issue #23 (2026-09-20): resolved.** A follow-up probe at the same location narrowed the bracket to [100 m rejected, 100.5 m accepted] and `AoiNormalizationOptions.MinimumFetchEnvelopeSide` (default 110 m per side, a 21 percent margin over the observed 0.01 km² floor) now widens a too-small fetch envelope automatically before `fetch`/`run` sends a request, for every AOI form (`docs/architecture/aoi-normalization-and-clipping.md`'s "Minimum fetch envelope, verified 2026-09-20" section). A live re-run of `run --parcel example-site-synthetic-parcel.geojson --parcel-format geojson --buffer 5` — B5 above, previously HTTP 400 — now completes with exit `0`; see the "Live OpenTopography scenario" update above for the full console output. The single-location and unconfirmed-server-formula caveats stand: this remains a 21 percent margin over one observed floor, not a proof that 110 m is sufficient everywhere.
- **Retention below budget is a known characteristic, not a bug**, but is worth revisiting: the whole-grid run left 1,906 points of a 15,000 budget unused (13,094 of 14,508 retained) because of how the coverage-floor pass groups candidates into blocks — see "Point reduction observed" above. Retaining every candidate outright whenever the candidate count is at or below the budget is a reasonable follow-up refinement. **Update, Issue #24 (2026-09-20): resolved.** `GridTerrainSimplifier.SimplifyCurvatureAware` now retains every candidate directly whenever `candidates.Count <= PointBudget`, bypassing the coverage-floor pass's per-block cap entirely in that case; the whole-grid re-run above now retains 14,508 of 14,508 rather than 13,094.
- **The opt-in live xUnit test now fails rather than skips.** With the opt-in flag and a valid key set, `OpenTopographyLiveTests.FetchesASmallRealAreaAroundTheExampleSiteLaneScenario` fails with `OpenTopographySourceMetadataException` instead of completing, because the live packaging this note documents does not match either shape the source currently handles. This will remain a failure, not a skip, until the packaging decision above lands. **Update, Issue #21 (2026-09-19): resolved.** The opted-in live suite now runs to completion: `total: 706 / failed: 0 / succeeded: 706 / skipped: 0`. Remaining follow-ups Issue #21 did not resolve: only NAD83 UTM zones are supported for the GeoTIFF-GeoKeys hybrid flow, so any other EPSG family, including NAD83(2011), still fails rather than being handled (`docs/architecture/cli-workflow.md`'s "Known limitations and follow-ups"); OpenTopography's undocumented minimum request area is still not padded automatically (same section's "No minimum-area padding" bullet); candidates-below-budget retention, described above in this same list, is unchanged; and the CLI `--unit` default remains a separately hardcoded literal rather than reading `LengthConverter.DefaultOutputUnit` (`docs/architecture/coordinate-transformation-and-units.md`'s "`LengthConverter.DefaultOutputUnit`" section). **Update, Issue #25 (2026-09-20): resolved.** The CLI `--unit` default no longer restates a separate hardcoded literal: `ProcessCommand`/`RunCommand` now default `--unit` to `LengthUnitTokens.DefaultToken` (`=> TokenOf(LengthConverter.DefaultOutputUnit)`), and `OptionTable`'s help text is built from the same source.
