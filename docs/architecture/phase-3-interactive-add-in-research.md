# Phase 3 interactive add-in research

This note records research findings for SolidGround Phase 3 (an interactive Revit 2027 add-in that turns a street address into coordinates, imports parcel boundaries, and presents a WPF dialog). It is a research record, not implementation work: no `SolidGround.Revit` or `SolidGround.Core` code was written or changed to produce it, and no Revit process was launched. Phase 3 has no implementation task open; `AGENTS.md`'s "Mission and current boundary" section already blocks Issue #16 and Issue #17 without an explicit task, and this note does not change that boundary. Findings below come from a same-day (2026-09-21) research swarm of ten sweep passes and ten independent verification passes, each anchored to a live web source, a direct reflection dump of the installed Revit 2027 (`27.0.10.13`) SDK, a live read of this repository's own code and GitHub issue history, or an explicit unverified/unresolved label. Only claims a verification pass marked confirmed or corrected are stated as fact below; everything else is labeled unverified, inferred, or an open gap.

## Basis

Ten sweep agents researched government/commercial/open geocoding, the area County and statewide/commercial parcel data, legal-description mapping, Revit 2027 boundary-entry APIs, a WPF dialog design, this repository's pipeline fit, and prior art. A second pass independently re-verified each sweep's claims, correcting several (a stale URL, a mischaracterized licence clause, an untraceable dollar figure, an incomplete API member list) and leaving several unresolved. This note restates only what survived that pass, or says plainly that it did not. A critic pass on 2026-09-21 flagged remaining gaps; a targeted revision the same day closed each one from already-gathered evidence or a fresh direct check (Mapbox's own pricing page; this repository's own `AoiSettingsFactory`/`AoiSelection` source), noted inline below, with no item left needing an unresolved-research placeholder. A further same-day owner-decision pass added a terms-and-cost review of six commercial parcel vendors (a reader and an independent verifier pass per vendor, plus a cost-and-education synthesis) and a live Regrid trial-token test against the fixture address, both folded into Goal (b) and the Owner decisions below.

## Purpose and boundary

Phase 3 adds four capabilities on the Phase 1/2 pipeline that already fetches, clips, simplifies, and places USGS 1 m terrain as a native toposolid with reversible provenance (`AGENTS.md`): (a) address-to-coordinates, (b) parcel boundary import, (c) how that boundary enters Revit and feeds the AOI pipeline, and (d) a WPF dialog. This note surveys options and recommends a direction; it does not authorize building any of it.

No pure-managed .NET package bundling an offline street-address database exists on NuGet: the `Geocoding.net` family are thin cloud-API wrappers, and the one "ReverseGeocoder" package found is a coarser, coordinate-to-place lookup targeting only .NET Framework 4.5, not `net10.0` (confirmed). The Census Geocoder matched the test address about 15.0 m from `AGENTS.md`'s stated parcel centre; the county's Esri proxy matched about 3.1 m away (both confirmed by haversine); no other provider's accuracy was tested live.

A static offline address index — OpenAddresses' CC0 the area County extract, the public-domain U.S. DOT National Address Database, or Overture Maps' addresses theme — was also considered as a key-free fallback to an online geocoder call; all three are licence-clean, though Overture's own terms vary per aggregated source (confirmed). None is adopted: no managed .NET GeoParquet reader or fuzzy address-matcher exists on NuGet, county-by-county coverage is uneven (the one endpoint this research tested for the area County now 404s), and Overture's addresses theme is still Alpha, with unstable feature IDs and explicitly partial U.S. coverage (confirmed) — rejected for tooling and coverage, not for licensing. Smarty, Precisely, and Radar were also evaluated and rejected from the table above: Smarty's data retention is Sales-Order/Product-Terms-specific rather than perpetual by default, and its "Internal Business Purposes" term bars redistribution; Precisely's geocoding pricing stays unpublished despite a new self-serve, no-card free trial; Radar's own pricing page confirms no free tier at all, only an annual-commitment quote (confirmed).

### Recommended direction

Default to the US Census Bureau Geocoder behind a new `IAddressGeocoder` interface in `SolidGround.Core`, mirroring the existing `IElevationSource` pattern. It is free, keyless, built from public federal data, and its TIGER-interpolated accuracy fits `AGENTS.md`'s own site-form-tool accuracy posture. Never default to the area County Esri proxy (no published terms, and a real risk of spending the county's paid credits) or to the public Nominatim instance (its policy requires a disclosed, deliberate choice, not an auto-wired default). Owner decision 1 (2026-09-21) adds both Geocodio and Esri's `forStorage=true` path as keyed opt-ins rather than a single fallback — Geocodio for its best-terms commercial fit, Esri's `forStorage=true` path for paid, storable results — each gated behind its own environment-variable key (`GEOCODIO_API_KEY`, `ARCGIS_API_KEY` or an equivalent name chosen in the issue), following the `OPENTOPOGRAPHY_API_KEY` convention, disabled by default.

### The area County endpoint, as verified

A live, tokenless point-in-polygon query at [withheld], [withheld] against `AGS_Parcels/MapServer/0` returns exactly one feature: `LOCATOR` [withheld], `PROP_ADD` "[withheld] the reference parcel", `SUBDIVISION` "[withheld] [withheld]", `LOTNUM` "[withheld]", `MUNICIPALITY` "[withheld]", `ZONING` [withheld], `YEARBLT` [withheld], and `SHAPE.STArea()` = [withheld] sq ft — matching `AGENTS.md`'s stated parcel almost exactly (confirmed, independently re-run). The same record is also reachable by `PROP_ADD LIKE '[withheld] ExampleSite%'` with no geometry input, useful for an address-driven lookup. Its `LEGAL` free-text field is blank even though `SUBDIVISION`/`LOTNUM` are populated; `DEEDBKPG`/`ASRBKPG` are the closest fields to a "plat book and page," but neither is documented as such. `maxRecordCount` is 6000 with a full advanced-query capability set (pagination, statistics, SQL expressions, datum-transformed queries), all confirmed live. The AGOL catalog item naming this service is owned by the county's GIS Service Center; the service itself physically runs on the county's own separate ArcGIS Enterprise Portal rather than inside that ArcGIS Online account, a nuance that does not affect reachability (corrected).

### Legal-description mapping

The county's Assessor "Real Estate Search" (by Locator Number, Name, Property Address, or Subdivision Name) is the practical key finder; its Deed Search page states plainly that the Locator Number needed for a paid Tapestry/Laredo deed or plat lookup is found there (confirmed verbatim). A companion "Subdivision Information Search" resolves a subdivision name to a Book and Page (confirmed). No literal "plat book and page" field exists in the open parcel layer itself. The parcel sits inside a historic private land grant: the area's own PLSS layer returns `TWP_TEXT`="Land", `RNG_TEXT`="Grant", `SEC_TEXT`="01929" at the exact test coordinates (confirmed, independently re-queried), consistent with the area's own record of French/Spanish-era land grants around the area adjudicated into U.S. Surveys (confirmed verbatim). [withheld] [withheld]'s own recorded legal-description wording sits behind a paid Tapestry/Laredo search or an in-person Recorder request and was not obtained — an explicit gap, not a negative finding. Whether Tapestry's own form exposes a metes-and-bounds field is likewise unresolved.

### Accuracy caveats and fixture licensing

the area County's Open Data Disclaimer states verbatim that it "makes no representations or warranties as to the completeness, accuracy, timeliness, or content of any data" and data "is used at one's own risk" (confirmed) — a general open-data disclaimer, not parcel-specific "not a survey" language; that a cadastral polygon is not a monumented boundary survey is industry background, not a quoted county position. The parcel layer's licence is a standard no-warranty government copyright notice, not an open licence — closer to OpenTopography's own terms than CC0/ODbL, but without Regrid's or ReportAll's resale bans. A single the reference parcel/[withheld] boundary, carried with that disclaimer text, is the only parcel-geometry fixture this research finds plausibly committable; that is offered for the owner's own review, not settled law.

### Recommended design

Add a pluggable `IParcelBoundarySource` in `SolidGround.Core`, mirroring `IElevationSource`. Make direct per-county ArcGIS REST queries the primary path, keyed by a small registry (base URL, layer index, field map), since the area has no statewide aggregator; not every county is REST-catalog-first (Jefferson County's public access is an Esri Experience Builder viewer). A geocoded point alone does not say which registry entry to query: the Census Geocoder's own `returntype=geographies` mode already returns the matching county's GEOID in the same call (read on source, tested live for the fixture address: the area County GEOID [withheld]), and that GEOID — or an equivalent spatial join against a county-boundary layer for a non-Census geocoder — should key the registry lookup rather than hardcoding one county. Owner decision 3 (2026-09-21) settles the commercial slot as a second, vendor-neutral `IParcelBoundarySource` reading a user-purchased county file from disk, not a keyed live API — see "Commercial parcel sources: terms and cost" below; never a default or fixture source, given the confirmed redistribution/derivative-work bans documented there.

## Goal (c): Revit entry point

### Verified 2027 API options

`PropertyLine` gained a public creation API in Revit 2027 — it had none before. This is confirmed three ways: a 2027-era Autodesk forum thread quotes an Autodesk DTS engineer stating flatly, of pre-2027 Revit, "the Revit API does not support creating it progrmmatically [sic]" (confirmed, full thread read); Autodesk's "What's New in Revit 2027" page states verbatim that "the `PropertyLine` class was exposed without its own dedicated methods and properties" before this release (confirmed); and reflection over the installed, hash-verified `27.0.10.13` `RevitAPI.dll` reproduces the new surface directly — 14 methods and 2 properties matching the full class-reference page exactly (corrected from an earlier count matching only the shorter What's-New list). The load-bearing members are `PropertyLine.Create(Document, IList<CurveLoop>)` (a second overload keyed on bearing/distance `PropertyTableEntry` rows also exists), `GetBoundary()`/`SetBoundary(...)`, `IsValidBoundary(...)`, `IsClosedLoop()`, and `Area`. `PropertyLine`'s runtime `Category` value could not be established by reflection (a per-instance, document-populated property) and remains an explicit, unresolved gap.

Weaker alternatives, all confirmed present by reflection: `Document.Create.NewModelCurve` (no schedule/tag/export semantics), view-specific detail lines, and a generic `DirectShape` wireframe container. `SiteSubRegion.Create(..., ElementId hostTopoSurfaceId)` also exists, but its parameter name and its `TopographySurface`-typed property tie it to the legacy `TopographySurface` element, whose own `[Obsolete]` attribute on `AddPoints` confirms it "deprecated in Revit 2024 with the introduction of the new Toposolid elements." Whether `SiteSubRegion` can host on a `Toposolid` was not tested live; treat this as inferred, not confirmed.

### Recommended representation

Owner decision 5 (2026-09-21) settles this: create a `PropertyLine` via the Revit 2027 `PropertyLine.Create(Document, IList<CurveLoop>)` overload, from the same `IList<CurveLoop>` that `BoundaryGeometryBuilder.BuildProfiles` already produces for `Toposolid.Create` (read from this repository's own Issue #15 code), in the same transaction as the toposolid. Both APIs accept the identical list type, so no new geometry code is needed, though this has not yet been exercised live. Do not pursue `SiteSubRegion` for this purpose.

### Shared coordinates

`ProjectLocation.GetProjectPosition`/`SetProjectPosition` and `BasePoint.SharedPosition` are confirmed present (carried over from Issue #15's own verified dump); Issue #15 deliberately only reads them today. Owner decision 6 (2026-09-21) keeps the read-only stance as the default and adds writing shared coordinates as an explicit dialog option, off by default, gated by a preflight check that refuses to write when the model already has shared coordinates set.

### Feeding the existing pipeline and provenance

`AoiSettingsFactory.Build` is the seam `RunDocumentPreflight` and `TerrainRequestSettings.Validate()` already share; a WPF dialog or a new settings-driven path only needs to produce an `AoiSettings`-shaped value to reuse it. Correction from this revision's own direct 2026-09-21 re-check of source: the CLI's flag surface does not call this factory — `SolidGround.Cli.Processing.AoiSelection.ToAreaOfInterest` independently mirrors its three constructions instead, a parallel implementation `AoiSettingsFactory`'s own doc comment names explicitly, not a shared call path. The same re-check found the pipeline-fit sweep's other cited mechanics accurate as stated: `IElevationSource`'s single-method shape, the `CliHost`/`FakeHttpMessageHandler` offline-test harness, and the `ToposolidCreatedHook` wiring below. A geocoder or parcel service should be added as a sibling to `IElevationSource`, with its own key provider and redaction helper — no existing redaction code is provider-agnostic. For provenance, extending `TerrainProvenance` to a new schema v3 with an optional address/parcel record reuses the existing assembler/renderer/reader pattern and can supply both the JSON export bundle and Issue #16's Extensible Storage schema through the `ToposolidCreatedHook` extension point already in code, confirmed still wired to `null` (`CreateToposolidCommand.cs`). Issue #16 remains open, labeled `status:ready`, unassigned, with the owner's own comment reading "Do not start without an explicit implementation task" (confirmed via a live `gh` query). Owner decisions 7 and 8 (2026-09-21) resolve both: the new fields go inside `TerrainProvenance` v3, with Issue #16's Extensible Storage entity gaining matching fields in a later schema version, and address/parcel selection resolves into today's `areaOfInterest.parcel` shape, with no new `AreaOfInterestKind`.

## Goal (d): WPF dialog

### Conventions impact

The current conventions (`revit-add-in-conventions.md`) fix a plain `TaskDialog` for the initial milestone and leave `UseWPF` for "once a WPF surface exists" — Phase 3 is that surface. The owner's other add-in's own dialogs (read-only reference) are pure code-behind with zero `.xaml`/BAML files, static adapter facades taking a Revit main-window handle and returning detached DTO records, with no MVVM framework and theming built only from `SystemColors`/`HighContrast`.

### Threading and owner-window pattern

`UIApplication.MainWindowHandle` is confirmed present in the installed `27.0.10.13` `RevitAPIUI.dll`. Own the dialog via `new WindowInteropHelper(window).Owner = commandData.Application.MainWindowHandle` and show it with modal `ShowDialog()` from inside `CreateToposolidCommand.Execute`, before today's Preflight/transaction. Any network call the dialog needs should use the same synchronous `Task.Run(...).GetAwaiter().GetResult()` bridge Issue #15 already locked in, so no Revit API touch happens off the Revit thread — this repository's own note already records a measured ~8-second freeze and a reproduced `InvalidOperationException` from touching the API off-thread.

### Theme

`Autodesk.Revit.UI.UIThemeManager.CurrentTheme` (`UITheme.Dark`/`Light`) and `UIApplication.ThemeChanged` are confirmed present in the installed `27.0.10.13` DLL and on the live `/2027/` class-reference page. Correction: these are Revit-2024-vintage members carried unchanged into 2027, not new-in-2027 — `blog.autodesk.io`'s "What's New in the Revit 2024 API" lists all of them as 2024 additions, so `AGENTS.md`'s rule against relying on earlier-version examples is satisfied by confirming they still exist in 2027, not by treating them as a 2027 feature. Read `CurrentTheme` once at construction and branch Dark/Light alongside the existing `SystemColors`/`HighContrast` branching; defer subscribing `ThemeChanged` until a modeless surface exists. DPI has no Revit-2027-specific documentation; the one Microsoft Learn page fetched in full does not say a hosted add-in's own top-level window automatically inherits the host process's DPI awareness — its literal table text reads the other way for a "hosted" framework, though that line more plausibly targets embedding interop, not an add-in's independent window. Treat DPI as a manual observation, not a design requirement.

### MVVM stance

Owner decision 11 (2026-09-21) adopts `CommunityToolkit.Mvvm` now instead of deferring it: latest stable 8.4.2, published 2026-03-25, confirmed MIT-licensed with zero extra dependencies on the `net8.0`/`net8.0-windows` asset groups a `net10.0-windows` project resolves against, Roslyn source generators only, no native code. It clears `AGENTS.md`'s dependency bar, and Phase 3's larger field count now outweighs the owner's other add-in's no-MVVM precedent — but the dialog itself stays pure code-behind with no `.xaml`/BAML files, for the isolation-context reason below; `UseWPF` turns on in the dialog issue, not this research note.

### A confirmed isolation-context risk

A Revit add-in DLL has no `App.xaml`, and GitHub issue `Nice3point/RevitToolkit#7` (same vendor as this repository's pinned CI-only reference packages) documents a real Revit-2025 bug, confirmed still live today: a WPF-referenced assembly loads twice, once into an isolated add-in's own context and once into Revit's default context, producing a `XamlParseException` tracked as still-open in `dotnet/wpf#1700`. `SolidGround.Revit` is deliberately isolated (`UseRevitContext=false`), so this is structurally relevant, not hypothetical. A pure code-behind dialog with zero `.xaml`/BAML files — matching the owner's other add-in's convention and this repository's embedded-icon mechanism — never invokes the BAML pack-URI resolver and so cannot hit this failure class.

### Content model and failure paths

Owner decision 9 (2026-09-21) adopts this full content model for the initial milestone, not a reduced first slice: address entry, geocode candidates, parcel candidates with a legal-description preview, AOI buffer, point budget (warned inline against the existing `Revit.ini` threshold guard), unit choice (`AGENTS.md`'s two foot definitions), level/toposolid-type dropdowns, a provenance/accuracy preview, and a final Preflight summary with Create/Cancel. Both dialog-Cancel and Preflight rejection should map to `Result.Cancelled`, never `Result.Failed`; an in-dialog lookup failure (a geocoder timeout, say) should stay inline and never reach `Execute`'s top-level catch.

## Cross-cutting

**Secrets and keys.** Any new HTTP-backed source follows the `OPENTOPOGRAPHY_API_KEY` pattern: an environment variable or .NET user secret, never committed or logged, with query strings redacted before logging. No existing redaction helper is provider-agnostic; a second HTTP source needs either a shared helper extracted first, or its own copy of the pattern. This same research swarm's own raw evidence files, kept in a local, uncommitted scratch workspace outside this repository, are not held to that standard: several unfiltered ArcGIS captures carry the fixture parcel's and roughly twenty neighbors' unredacted owner names and mailing addresses, and several cached web-search results carry incidental third-party Google Maps API keys picked up from scraped image URLs. Neither belongs in this repository; both need scrubbing from that workspace before any reuse or archival, independent of anything committed here.

**Licensing for a public repository.** Government/public-domain sources (the Census Geocoder, the area County's parcel layer under its no-warranty notice) are the only sources safe as defaults or as a committed-fixture basis. If the owner opts into OSM Nominatim, the OSMF's board-endorsed guideline confirms a single cached geocoding result does not trigger ODbL share-alike, given attribution. Regrid, ReportAll, ATTOM, CoreLogic/Cotality, LightBox, and Esri's Regrid-sourced "Living Atlas" layer must never be committed as fixtures or enabled by default, given their confirmed redistribution bans.

**Dependency policy.** Every provider surveyed is a plain REST/JSON API reachable by `HttpClient`/`System.Text.Json`; none needs a NuGet package. Several vendor SDKs are unsuitable regardless: Esri's "ArcGIS Maps SDK for .NET" bundles native binaries and targets .NET 8, not .NET 10; Mapbox's C# SDK is archived; `Azure.Maps.Search` is still a prerelease beta.

**Test strategy.** Mirror the offline-by-default pattern: `FakeHttpMessageHandler` plus `CliHost` for any new geocoder/parcel verb, and a real opt-in online test gated on its own flag and key, skipping rather than failing when absent, like the existing OpenTopography test. Groundit's own account of needing defensive vertex cleanup before external polygon geometry reaches Revit's `CurveLoop` APIs (read on source, not independently re-verified by this swarm) is a concrete risk worth a Core-level test once an external parcel polygon is ingested.

## Owner decisions (2026-09-21)

1. **Geocoder.** Default: US Census Bureau Geocoder (keyless). Keyed opt-ins: Geocodio and Esri's `forStorage=true` path, each behind its own environment-variable key, off by default. Basis: free/federal by default; the paid paths cover tighter accuracy or storable results.
2. **Parcels.** A pluggable `IParcelBoundarySource` with a per-county registry (base URL, layer index, field map) keyed by the geocoder's Census GEOID; the area County's `AGS_Parcels`/`MapServer/0` is entry one. Never the county's Esri proxy; never auto-wire public Nominatim. Basis: the area has no statewide aggregator, the proxy has no published terms, and Nominatim's own policy bars a silent default.
3. **Commercial parcel slot.** Not a keyed API: a vendor-neutral local-file `IParcelBoundarySource` reading a user-purchased county file from disk (GeoJSON first; GeoPackage or Shapefile only if a managed reader already in the dependency set can parse it, otherwise GeoJSON only), with Regrid's Data Store the area County Standard Schema purchase ($300 one-time, 1-year licence, permits internal-tool loading) as the reference purchase. Basis: the terms-and-cost passes below found every live commercial API bars permanent storage, derivation, or redistribution outright, or (ReportAll) leaves it unresolved.
4. **Regrid trial test.** Confirmed empty results for the fixture address (outside the trial's seven-county coverage) and recorded the Dallas County Standard-schema field list for future redaction — see "Regrid trial observation" under Goal (b). Basis: documents real trial coverage and the redaction list before any keyed integration is designed.
5. **Boundary in Revit.** Create a `PropertyLine` via `PropertyLine.Create(Document, IList<CurveLoop>)` in the same transaction as the toposolid, from `BoundaryGeometryBuilder`'s existing curve loops. Basis: identical list type, so no new geometry code, and one atomic transaction.
6. **Shared coordinates.** An explicit dialog option, default off, with a preflight check refusing to write when the model already has shared coordinates set. Basis: keeps Issue #15's verified read-only default while allowing an informed opt-in.
7. **Provenance.** `TerrainProvenance` moves to schema v3 with an optional address/parcel record; Issue #16's Extensible Storage entity gains matching fields later. Basis: reuses the existing assembler/renderer/reader pattern instead of a sibling document.
8. **AOI plumbing.** An address/parcel choice resolves into today's parcel GeoJSON/WKT AOI shape; no new `AreaOfInterestKind`. Basis: the existing shape already fits a parcel polygon.
9. **Dialog.** Ship the full content model (address entry through Preflight summary; see Goal (d)) in the first milestone, not a reduced first slice. Basis: one complete surface serves the dialog's own dependencies better than a partial one.
10. **Fixture.** A single the reference parcel/[withheld] parcel may be committed as an offline fixture, stripped of `OWNER_NAME`, `OWN_ADD`, `OWN_CITY`, `OWN_STATE`, `OWN_ZIP`, `CAREOF`, carrying the county's no-warranty notice verbatim, after the fixture-security test passes. Basis: `AGENTS.md`'s existing fixture-inspection rule.
11. **MVVM.** Adopt `CommunityToolkit.Mvvm` 8.4.2 now; the dialog stays pure code-behind, no XAML/BAML; `UseWPF` turns on in the dialog issue. Basis: the larger field count now justifies the toolkit, and code-behind avoids the confirmed isolated-context `XamlParseException` risk.
12. **Redaction.** Extract a shared, provider-agnostic HTTP redaction and key-resolution helper into `SolidGround.Core` as its own issue, before the geocoder issue; OpenTopography, both geocoders, and the county source all use it. Basis: no existing helper is provider-agnostic.
13. **Process.** This note ships as documentation; the planning file records the issues as created; Phase 3 implementation still needs its own explicit task; the `AGENTS.md` boundary-sentence edit is proposed in the planning file only, never applied here. Basis: matches `AGENTS.md`'s existing boundary rule and Issue #16/#17's blocked status.
