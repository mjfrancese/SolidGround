# Revit 2027 verification and host design

Issue #13, "[Phase 2] Reverify Revit 2027 APIs and lock the host design," verifies every Revit-specific API and configuration that `docs/architecture/revit-add-in-conventions.md` left open, against the installed Revit 2027 SDK or Autodesk's current 2027 documentation, and locks the thin-host design and manual integration test plan Phase 2 needs before Issue #14 scaffolds `SolidGround.Revit`. This note records that verification, completed on 2026-09-20. It changes nothing in the owner decisions or already-adopted conventions `docs/architecture/revit-add-in-conventions.md` recorded on 2026-09-20; it verifies the 14 items that note deferred to Issue #13, plus three items from Issue #13's own broader GitHub scope (fetched live for this note with `gh issue view 13`): Toposolid creation signatures and boundary and point requirements, level, type, shared-coordinate, and units APIs, and the delta between Autodesk's 2027.2-documented API surface and the installed 2027.0.x build. Section 4 below reports every place the evidence conflicts with `AGENTS.md` or the approved conventions for the owner's direction, per `AGENTS.md`'s own governance rule; the owner resolved all three on 2026-09-20, recorded there.

## Verification results

### 1. Isolated add-in context manifest syntax

> Isolated add-in context manifest syntax: exact element names for `UseRevitContext`, `ContextName`, `Dependencies`, `PublicAssemblies`, `UseAllContextsForDependencyResolution`. The owner's other add-in's manifest predates the feature; cite the Revit 2027 SDK or Autodesk's manifest docs directly.

**Verdict: verified-with-caveat.**

**Evidence.** The installed `RevitAddInUtility.dll` (27.0.10.13) declares `RevitAddInManifestSettings` with exactly these members (installed-sdk, `verify/V01/V01.md`):

```
public System.String ContextName { get; set; }
public System.Collections.Generic.List<Autodesk.RevitAddIns.AddInDependencyBase> Dependencies { get; }
public System.Collections.Generic.List<System.String> PublicAssemblies { get; }
public System.Boolean UnifyInAddInManager { get; set; }
public System.Boolean UseAllContextsForDependencyResolution { get; set; }
public System.Boolean UseRevitContext { get; set; }
```

`RevitAddInManifest.ManifestSettings` confirms this block belongs to the whole manifest file, not to one `<AddIn>` entry. Autodesk's "Add-in Dependency Isolation" guide (autodesk-2027-doc) states the default directly: "Developers can set the option \"UseRevitContext\" to false per add-in manifest... The default for add-ins where this is not specified is \"true\"." A hand-authored manifest round-tripped through `AddInManifestUtility.GetRevitAddInManifest` (local-experiment) confirmed `<ManifestSettings>` sits as a sibling of `<AddIn>` under `<RevitAddIns>`, that `<UseAllContextsForDependencyResolution>` defaults to `false` and is omitted from `RevitAddInManifest.SaveAs()` output whenever it equals that default, and that a manifest with no `<ManifestSettings>` block at all loads with `UseRevitContext = True`, silently, with no warning.

**Conclusion.** `<ManifestSettings>` wraps six children in a fixed serialization order: `<UseRevitContext>` (boolean, default `true` when absent), `<UnifyInAddInManager>` (boolean, default `false`, not one of this item's five named elements), `<ContextName>` (string, optional), `<UseAllContextsForDependencyResolution>` (boolean, default `false`), `<PublicAssemblies>` (wraps `<Assembly>` path-string children), and `<Dependencies>` (wraps `<DependsOnClientId ClientId="{guid}">`/`<DependsOnContext ContextName="{name}">` elements, each with optional `<AssemblyName>` children). The recommended manifest text is:

```xml
<?xml version="1.0" encoding="utf-8"?>
<RevitAddIns>
  <AddIn Type="Application">
    <Name>SolidGround</Name>
    <Assembly>SolidGround.Revit.dll</Assembly>
    <AddInId>00000000-0000-0000-0000-000000000000</AddInId> <!-- mint a fresh GUID once, then pin it -->
    <FullClassName>SolidGround.Revit.SolidGroundApplication</FullClassName>
    <VendorId>SolidGround</VendorId>
    <VendorDescription>SolidGround</VendorDescription>
  </AddIn>
  <ManifestSettings>
    <UseRevitContext>False</UseRevitContext>
    <ContextName>SolidGround</ContextName>
    <UseAllContextsForDependencyResolution>False</UseAllContextsForDependencyResolution>
  </ManifestSettings>
</RevitAddIns>
```

Autodesk's own T2 and T12 isolation-feature sample manifests write `<ClientId>`, not `<AddInId>`, as a direct child of `<AddIn>`; both spellings parse through `AddInManifestUtility`. Which one is correct on the primary `<AddIn>` element is item 11's question, not this item's five named elements, and item 11 below settles it in favor of `<AddInId>`.

**Consequence for SolidGround.Revit.** Build the shipped `SolidGround.addin` as a static template, not via `RevitAddInManifest.SaveAs()`: that API silently omits any `ManifestSettings` child that equals its default, including `UseAllContextsForDependencyResolution`, which would violate `AGENTS.md`'s "set explicitly" requirement if a future deploy step generated the file that way. Add a check asserting the shipped manifest always contains a literal `<UseRevitContext>False</UseRevitContext>` line, since a forgotten assignment produces no `<ManifestSettings>` element at all and the add-in silently loads into Revit's shared default context.

**Deferred to manual testing.** Whether isolation actually isolates two add-ins with conflicting same-named dependencies; whether an unspecified `UseRevitContext` really defaults to the shared context at Revit's own runtime load; whether `ContextName` merges two add-ins' contexts; whether `<ClientId>` parses identically to `<AddInId>` at Revit's own startup, not just through `AddInManifestUtility`; whether lowercase `false`/`true` casing parses at Revit's own startup. See section 6.

**Verdict: verified-with-caveat.**

### 3. Per-user Add-Ins folder name for Revit 2027

> The exact per-user Add-Ins folder name for Revit 2027, `%APPDATA%\Autodesk\Revit\Addins\2027`. The owner's other add-in confirms only the 2026 pattern; confirm the `2027` segment against the installed product.

**Verdict: verified-with-caveat.**

**Evidence.** `RevitProductUtility.GetAllInstalledRevitProducts()`, run out-of-process against the installed `RevitAddInUtility.dll` (local-experiment, `verify/V03/V03.md`), reports for the Revit 2027 product: `CurrentUserAddInFolder=%USERPROFILE%\AppData\Roaming\Autodesk\Revit\AddIns\2027` (the literal expansion of `%APPDATA%`), a bare four-digit year with no "Revit " prefix. Three independent enumeration methods that read a directory's true stored name rather than echo an operator-typed path (`Get-ChildItem` on the parent directory, `[System.IO.Directory]::GetDirectories()`, native `cmd /c dir /b`) agree the real, on-disk casing is `Addins` (lowercase "i"), matching `AGENTS.md`'s own existing text, across all three real Revit Addins directories on this machine (per-user 2026, all-users old-location 2026, all-users new-location 2027). Autodesk's T1 "Add-in Registration" page instead states the per-user path as `...\Addins\Revit 2027\`, with a "Revit " prefix; the identical wording appears in the 2026 build of the same page (2026-fallback) where it does not describe the real, currently-loaded per-user 2026 folder, which is `...\Addins\2026\`. Autodesk's T12 "Add-in Installation folder changes" table, confirmed to sit in the base-2027 section (not 2027.1/2027.2), instead uses the bare `20XX` convention and the `Addins` casing, agreeing with the installed product.

**Conclusion.** `%APPDATA%\Autodesk\Revit\Addins\2027` is the confirmed exact path, including casing; the per-user 2027 folder does not exist yet on this machine (`Test-Path` false for both castings), consistent with Revit 2027 never having launched here, but its `Addins` parent already exists. `RevitAddInUtility`'s own reported casing, `AddIns` (capital I), does not match true on-disk convention anywhere checked and should not be cited for casing, though NTFS's case-insensitivity means this has no functional effect.

**Consequence for SolidGround.Revit.** No change needed to the already-adopted path string in `docs/architecture/revit-add-in-conventions.md` section 7. The deploy script's "fails closed on any missing file" discipline should extend to creating the missing `2027` directory level itself, since only that leaf is absent; its `Addins` parent already exists and is a shared, multi-vendor location (the per-user 2026 folder already holds the owner's other add-in and RevitMcp side by side, and both all-users folders already hold first-party Autodesk manifests or pyRevit), so a future all-user write there should be an idempotent create-if-missing step, not the atomic-rename treatment reserved for SolidGround's own exclusively-owned per-user payload.

**Deferred to manual testing.** Whether Revit 2027 actually enumerates and loads a manifest placed in this folder at startup; whether Revit would also honor a populated `...\Addins\Revit 2027\` folder as a legacy alternate path. See section 6.

### 4. `Application.AllUsersAddinsLocation` shape

> `Application.AllUsersAddinsLocation`, required for any all-user scenario. The owner's other add-in has no example; verify the property's shape against the Revit 2027 API before any code reads it.

**Verdict: verified-with-caveat.**

**Evidence.** Both `Autodesk.Revit.ApplicationServices.Application` and `Autodesk.Revit.ApplicationServices.ControlledApplication` independently declare (installed-sdk, `verify/V04/V04.md`):

```
public System.String AllUsersAddinsLocation { get; }
public System.String CurrentUserAddinsLocation { get; }
```

instance, get-only, `System.String`, with no shape drift against Autodesk's 27.2.0.0-labelled documentation pages for both classes. Neither class has a public constructor, so a deploy script that runs outside Revit cannot obtain an instance. `IExternalApplication.OnStartup(UIControlledApplication application)`'s complete Properties block (installed-sdk) is exactly `ActiveAddInId`, `ControlledApplication`, `IsLateAddinLoading`, `IsViewerModeActive`, `LoadedApplications`, `MainWindowHandle`, `ProductIsRS`, with no `Application`-typed member, so `OnStartup` code can only reach the value as `application.ControlledApplication.AllUsersAddinsLocation`; command-time code reaches the literal `Application.AllUsersAddinsLocation` wording via `commandData.Application.Application.AllUsersAddinsLocation`. Autodesk's T12 "Add-in Installation folder changes" table names `Application.AllUsersAddinsLocation` directly as the property whose value changed with the `ProgramData`-to-`Program Files` migration, and `RevitAddInUtility.RevitProduct.AllUsersAddInFolder` (local-experiment) reports `C:\Program Files\Autodesk\Revit\AddIns\2027` for the Revit 2027 product, consistent with that documented migration but not yet cross-checked against a live call inside a running Revit 2027 process.

**Conclusion.** The property's shape is confirmed. `RevitAddInUtility.RevitProduct.AllUsersAddInFolder` is a documented-as-intended, twice-reproduced-offline candidate for the same value, not yet a live-cross-checked "proven" equivalent, because Revit 2027 has never launched under this profile.

**Consequence for SolidGround.Revit.** No code should cache a hardcoded all-user path; call the property dynamically. `AGENTS.md`'s sentence "runtime code that needs the all-user path must read `Application.AllUsersAddinsLocation`" is imprecise for `OnStartup`/`OnShutdown` specifically, since `UIControlledApplication` has no `Application`-typed member; the only expression that compiles there is `application.ControlledApplication.AllUsersAddinsLocation`. This wording gap was reported for the owner in section 4 below, where the owner's direction, recorded 2026-09-20, corrects `AGENTS.md` to name both call sites. No current Issue #14 code path needs to resolve an all-user path at all, since the initial milestone installs per-user only.

**Deferred to manual testing.** Whether `OnStartup`'s logged value actually equals `RevitAddInUtility`'s reported value inside a real, running Revit 2027 process; whether `OnStartup`-time and command-time reads agree within one session. See section 6.

### 5. `CopyLocalLockFileAssemblies` under `net10.0-windows`

> Whether a Revit add-in class library still fails to copy `PackageReference`/lock-file assemblies to `bin/` by default under `net10.0-windows`. The owner's other add-in's `CopyLocalLockFileAssemblies` workaround was observed under `net8.0-windows`; SDK behavior can change between target frameworks.

**Verdict: verified-with-caveat.**

**Evidence.** A clean-rebuilt `net10.0-windows` class library referencing `NetTopologySuite` 2.6.0 (local-experiment, `verify/V05/V05.md`) leaves no `NetTopologySuite.dll` in `bin/Release/net10.0-windows/` by default; setting `<CopyLocalLockFileAssemblies>true</CopyLocalLockFileAssemblies>` copies it, at 902,656 bytes, SHA-256-identical to the copy already sitting in the shared NuGet global-packages cache this repository's own build also uses. A second experiment, a `net10.0-windows` "Host" project taking a plain `ProjectReference` to a `net10.0` "CoreLike" project carrying `SolidGround.Core`'s exact pinned package versions, confirms `ProjectReference` alone copies only the referenced project's own `.dll`/`.pdb`, never its `PackageReference`-resolved package assemblies; setting `CopyLocalLockFileAssemblies=true` on the *consuming* Host project (never on `CoreLike`) pulls in the entire transitive package graph, `NetTopologySuite.dll` and `ProjNET.dll` both. Microsoft's own `learn.microsoft.com` documentation for the property states the default varies by output type ("false" for class libraries, "true" for console applications), confirmed to match by direct query that neither experiment project sets `<OutputType>` (both default to `Library`, the same output type `SolidGround.Revit` will have).

**Conclusion.** Confirmed unchanged under `net10.0-windows`/SDK `10.0.401`. `CopyLocalLockFileAssemblies` must be set on the `ProjectReference`-consuming project, never the referenced one; `SolidGround.Core.csproj` needs none, `SolidGround.Revit.csproj` needs it, exactly as already adopted.

**Consequence for SolidGround.Revit.** With the property set, an ordinary build leaves `SolidGround.Revit.dll`, `SolidGround.Core.dll`, `NetTopologySuite.dll`, and `ProjNET.dll` sitting flat in `bin/Release/net10.0-windows/`. A flat directory walk of that folder cannot by itself satisfy `AGENTS.md`'s "fails closed on any missing file" requirement, because a walk has no independent notion of what should be present, only of what is present, so it cannot detect a dependency that silently failed to copy. The deploy script needs an independently derived expected set; `SolidGround.Revit.deps.json` (which lists the full transitive package set even in a build where the DLLs were not physically copied) and the already-committed `packages.lock.json` are both viable sources. `RevitAPI.dll`/`RevitAPIUI.dll` must never appear in the deployed folder; that check needs no expected set at all, since their expected count is always zero.

**Deferred to manual testing.** Whether Revit's isolated add-in loader actually needs the physical co-located copies this property produces, versus resolving them some other way; the positive and negative controls in section 6 below settle this.

### 6. WPF threading and `ExternalEvent` rules

> WPF-in-Revit threading rules: a WPF dispatcher callback is not Revit API context, and modeless work must go through `ExternalEvent`. Cited from a Revit 2026 add-in and an unimplemented the owner's other add-in spec; re-verify before any modeless UI.

**Verdict: verified-with-caveat.**

**Evidence.** `ExternalEvent`, `IExternalEventHandler`, and `ExternalEventRequest` exist in the installed 27.0.10.13 build with the exact shape the 27.2.0.0-labelled documentation shows (installed-sdk, `verify/V06/V06.md`): `ExternalEvent.Create`/`CreateJournalable`/`Dispose`/`Raise`/`IsPending`; `IExternalEventHandler.Execute(UIApplication)`/`GetName()`; `ExternalEventRequest.Accepted=0/Pending=1/Denied=2/TimedOut=3`. Autodesk's "External Events" guide (autodesk-2027-doc) states: "When the ExternalEvent.Raise() method is called, Revit will wait for an available Idling timecycle and then call the IExternalEventHandler.Execute() method," and that mechanism "operates similarly to the Idling event." The exact phrase "not Revit API context" is not on any 2027 page found; the term "API context" is genuine 2027 vocabulary but appears on a different page (the "Commands" guide, discussing `PostCommand()`), not tied there to `ExternalEvent` or WPF. The guide's own code sample is `System.Windows.Forms.Form`, not WPF, and a fresh grep of every fetched ExternalEvent-related 2027 page for "WPF" or "Dispatcher" returns zero matches.

**Conclusion.** The three types and the substantive rule (a call from a non-Revit thread must go through `ExternalEvent.Raise()`, and Revit later calls `IExternalEventHandler.Execute()` when no other command or edit mode is active) are confirmed. The rule is about which thread calls the Revit API, not specifically about WPF: a plain background-thread continuation that skips `ExternalEvent` trips the identical rule with no WPF involved at all.

**Consequence for SolidGround.Revit.** `SolidGround.Core`'s only elevation-acquisition entry point, `IElevationSource.AcquireAsync`, returns `ValueTask<ElevationAcquisition>` and performs a real network fetch. `CreateToposolidCommand.Execute` is Revit's fixed, synchronous, `Result`-returning signature and cannot itself carry the `async` modifier (confirmed by a local `CS1983` compile failure). Section 5 locks the initial-milestone default for this choice: `Execute` blocks synchronously on the acquisition, through `Task.Run(() => source.AcquireAsync(request, cancellationToken).AsTask()).GetAwaiter().GetResult()`, staying in valid API context throughout, rather than offloading to a background thread, which would reproduce this item's own "not Revit API context" failure the moment the continuation touches the `Document`, requiring the same `ExternalEvent` pattern even before any WPF surface exists. This is an implementation-level default, not an owner decision; Issue #15 may change it with a recorded reason. Once a WPF modeless surface is eventually designed, per the conventions note's still-deferred `UseWPF` decision, the add-in must create the `ExternalEvent` and its handler during `OnStartup`/command execution, have the WPF window's event handlers call only `ExternalEvent.Raise()`, and put all Revit API work inside `IExternalEventHandler.Execute(UIApplication)`.

Two designs are both evidence-backed for supplying points, and documentation alone does not settle which is better: Option A, the single combined `Toposolid.Create(document, profiles, points, topoTypeId, levelId)` call, documents no point-validity condition at all; Option B, `Toposolid.Create(document, profiles, topoTypeId, levelId)` followed by `GetSlabShapeEditor().Enable().AddPoints(points)`, adds one documented distinctness exception but still leaves boundary containment as Remarks-only prose, and needs an extra `Enable()`/`Regenerate()` step.

**Consequence for SolidGround.Revit.** `profiles` must stay a general `IList<CurveLoop>`, not assumed to be a single loop, since `AGENTS.md`'s buffered-polygon AOI contract can produce holes. `CreateToposolidCommand`'s Preflight, which runs strictly before any transaction opens, can verify: `profiles` non-empty, individually closed, planar, parallel to the horizontal plane, non-intersecting, with no helical curve; `points` has at least three entries; the resolved `levelId`/`topoTypeId` actually resolve via `FilteredElementCollector`; no constructed argument is null. Preflight structurally cannot verify that a transaction is open, since none exists yet when it runs; that is a control-flow property of `Execute` itself, not a Preflight check. SolidGround's own geometry code should independently check XY-distinctness and boundary-containment of the decimated point set before calling either creation path, rather than rely on undocumented Revit enforcement for either condition.

**Deferred to manual testing.** Whether Option A silently tolerates, clamps, or throws for an out-of-boundary or duplicate point, and the same question for Option B's boundary-containment case; manual test step 8 covers both. Invalid `ToposolidType`/`Level` id behavior and floating-point tolerance for "planar"/"parallel to horizontal" are not exercised by any step in section 6, since every step's precondition opens a project document and none supplies an invalid id or a near-planar boundary; these gaps are carried to Issue #15 directly rather than settled by this plan. **Command flow.** `CreateToposolidCommand.Execute(ExternalCommandData commandData, ref string message, ElementSet elements)` (item 13) carries `[Transaction(TransactionMode.Manual)]` plus `[Regeneration(RegenerationOption.Manual)]` (item 10) and a top-level `catch (Exception ex) when (ex is not OutOfMemoryException and not StackOverflowException)` boundary, both already fixed by convention. A read-only Preflight step runs first, before any transaction opens (item 15): the document is a project document, not a family document (`Document.IsFamilyDocument` false); AOI and boundary present, closed, planar, parallel to horizontal, non-intersecting, no helical curves; a decimated point set with at least three points, XY-distinct, and contained within the boundary (SolidGround's own independent check, since neither distinctness nor containment is confirmed enforced by either `Toposolid.Create` overload, item 15); a `Level` and `ToposolidType` found by the selection rule below (items 15, 16); the configured point-budget value is present and a valid positive number, matching conventions-note section 4's "budget configured" check; no constructed argument is null; an API key resolvable. Preflight rejection returns `Result.Cancelled`, per the existing convention, still unconfirmed against Revit 2027's actual Undo-stack behavior (item 2, deferred, see section 6). The boundary between `Execute` and `SolidGround.Core` crosses in decimal feet, tagged with the exact foot definition `LengthConverter` used; the add-in converts through `UnitUtils.ConvertToInternalUnits`/`ConvertFromInternalUnits` with the matching `ForgeTypeId` (`UnitTypeId.Feet` or `UnitTypeId.UsSurveyFeet`) before any coordinate crosses into Revit's own internal units (item 16). Because `Execute` cannot itself carry the `async` modifier (item 6), `Execute` blocks synchronously on the acquisition, shaped as `Task.Run(() => source.AcquireAsync(request, cancellationToken).AsTask()).GetAwaiter().GetResult()`, with every Revit API call, Preflight, the transaction, and the dialog, staying on the Revit thread inside `Execute` before and after that call, and no Revit API call ever made from the thread-pool thread. This is the locked initial-milestone default, not an owner decision; Issue #15 may change it with a recorded reason. `SolidGround.Core` is Revit-free, and a grep on 2026-09-20 found every one of its 17 `await` expressions uses `ConfigureAwait(false)` (17 awaits, 17 `ConfigureAwait(false)` in `src/SolidGround.Core`), so no continuation ever needs the Revit thread; the `Task.Run` wrapper additionally starts the chain with no synchronization context, which removes the classic blocking-wait deadlock even if a future Core change forgets `ConfigureAwait(false)`. The UI freeze during acquisition is accepted for the initial milestone because the conventions allow only one modal `TaskDialog` and no modeless UI; `ExternalEvent`/`IExternalEventHandler` (item 6) is deferred to a later milestone if a progress or cancel surface is wanted. As an Issue #15 follow-up, this note recommends enforcing CA2007 (ConfigureAwait) as an error for `SolidGround.Core`, so the invariant the bridge relies on is checked by the build, not only by a one-time grep.

One `Transaction` wraps both `Toposolid.Create` and the Extensible Storage attachment. The default creation call is the single combined overload, `Toposolid.Create(document, profiles, points, topoTypeId, levelId)` (item 15, "Option A"), since it needs one call inside the one transaction and matches the "single Transaction" design; SolidGround's own Preflight and point-simplification code, not the API, is responsible for XY-distinctness and boundary-containment, since neither is confirmed enforced by this overload. If the manual test in section 6 shows the combined overload accepts invalid points silently, switch to the profiles-only overload followed by `GetSlabShapeEditor().Enable().AddPoints(points)` inside the same transaction (item 15, "Option B"), which at least throws for non-distinct XY points, and call `document.Regenerate()` before the transaction commits, per that path's own documented remark. Immediately after `Create` succeeds, in the same transaction, obtain the schema via `Schema.Lookup(<pinned schema GUID>) ?? BuildSchema()` rather than calling `SchemaBuilder`/`Finish()` unconditionally (item 8): guarding with `Schema.Lookup` first, matching the owner's other add-in's own established idiom, avoids depending on the still-open question of whether a second `Finish()` call under the same GUID throws. `BuildSchema()` itself wraps `new SchemaBuilder(<pinned schema GUID>)`, `SetSchemaName`, `SetReadAccessLevel(AccessLevel.Public)`, `SetWriteAccessLevel(AccessLevel.Vendor)`, `SetVendorId("SolidGround")`, `SetDocumentation`, one `AddSimpleField`/`AddArrayField` per provenance field with `SetSpec(SpecTypeId.Length)` on every length-quantity double, and `Finish()`. Then build `new Entity(schema)`, `Entity.Set<T>(field, value[, unitTypeId])` for every field, `Element.SetEntity(entity)`.

Failure handling wraps the whole `Execute` body: `FailureHandlingOptions`/`IFailuresPreprocessor` registered via `Transaction.SetFailureHandlingOptions` observe deferred regeneration failures the point-threshold enforcement might raise (item 9), in addition to the ordinary `try`/`catch`. A single failure surfaces as one native `TaskDialog` (item 13), full-sentence body, `MainInstruction` kept to Autodesk's own three-line guidance where practical; a long problem list is capped in the dialog body (using `ExpandedContent` for overflow, per Autodesk's own guidance) and the complete list is written to the log folder, naming the path in the dialog. Diagnostic and event-handler code wraps in try/catch that logs and swallows; it never throws back into Revit's own pipeline.

**Extensible Storage schema shape.** As verified under item 8: `AccessLevel.Public` read, `AccessLevel.Vendor` write, `VendorId` "SolidGround" (case-normalized by Revit itself, so case never needs to match the manifest's `VendorId` byte for byte). A stable schema GUID plus an explicit `schemaVersion` field (already adopted in the conventions note section 11, confirmed by item 8 to have no native alternative). Schema construction is guarded by `Schema.Lookup(<pinned schema GUID>)`, matching the owner's other add-in's own idiom (item 8), so `SchemaBuilder`/`Finish()` runs at most once per Revit session no matter how many times `CreateToposolidCommand` executes. Field types: `string` for source dataset, collection-date range, quality level, horizontal and vertical datum, output-unit label, and informational version; `int`/`long` for original and retained point counts; `double` with `SetSpec(SpecTypeId.Length)` for elevation minimum and maximum and each local-origin-offset component (Core cannot type these as a native `XYZ`, so the offset is three independent doubles); `Guid` for MVID; and a hex `string` for the SHA-256 build hash, the lower-risk default over an `AddArrayField(name, typeof(byte))` array field, whose exact accepted container type is unconfirmed (item 8, deferred).

**Level and type selection rule.** `levelId` resolves to the existing `Level` with the lowest `Level.Elevation` among `new FilteredElementCollector(document).OfClass(typeof(Level))` (`Level.Elevation` is a confirmed installed-sdk member, `public System.Double Elevation { get; set; }`, `Autodesk.Revit.DB.Level.txt`), ties broken by ordinal `Name` (`Element.Name` is a confirmed installed-sdk member, `public System.String Name { get; set; }`, `Autodesk.Revit.DB.Element.txt`), unless a configured level name, a Core-level configuration value for the initial milestone, consistent with the conventions note section 5's "no settings file until needed," matches a `Level.Name` exactly. The initial milestone never calls `Level.Create`; a document with no `Level` is a Preflight rejection (`Result.Cancelled` with one `TaskDialog`). A family document, `Document.IsFamilyDocument` true (a confirmed installed-sdk member, `public System.Boolean IsFamilyDocument { get; }`, `Autodesk.Revit.DB.Document.txt`), is also a Preflight rejection. This keeps the single transaction to `Toposolid.Create` plus the entity attachment and avoids creating a datum element as a side effect. `topoTypeId` resolves via `new FilteredElementCollector(document).OfClass(typeof(ToposolidType))` (item 15); there is no `ElementTypeGroup.ToposolidType` shortcut. Among the collected `ToposolidType`s, the command uses the type whose `Name` equals a configured type name if one is configured, else the first by ordinal `Name`; the initial milestone never creates or duplicates a `ToposolidType`; a document with no `ToposolidType` is a Preflight rejection. Both selection rules are locked as implementation-level defaults, not owner decisions; Issue #15 may change either with a recorded reason. The chosen `Level` and `ToposolidType` names and `ElementId` values are written to the log; they are not added to the provenance field list, which stays as verified under item 8.

**Coordinate mapping rule.** `InternalOrigin.Position` is always `(0,0,0)` (item 16). The initial milestone constructs `XYZ` points directly in Revit's internal coordinates and makes no change to `ActiveProjectLocation`, `BasePoint`, or `SiteLocation`; no shared-coordinate change happens as a side effect of toposolid creation. Provenance records the complete local-origin offset already required by `AGENTS.md`, plus, as a recommended addition, the project base point and survey point positions (`BasePoint.Position`/`SharedPosition`) at creation time, so a later shared-coordinate change can be reconciled against what SolidGround actually saw.

**Point-budget rule.** The application default stays near 15,000 (`AGENTS.md`'s existing instruction), configurable, comfortably under the confirmed 20,000 default for `NativeToposolidMaxPointThreshold`/`LinkToposolidMaxPointThreshold` (item 9). No documentation source confirms either setting gates the `Toposolid.Create(document, profiles, points, topoTypeId, levelId)` combined-overload API path SolidGround calls; the `IFailuresPreprocessor` registration above is the defensive compensation for that gap, not a substitute for the manual test in section 6.

**Settings and log locations.** Unchanged from the already-adopted conventions: `%ProgramData%\SolidGround\Revit\` for the settings file, `%ProgramData%\SolidGround\Revit\Logs\` for logs, `System.Diagnostics.Trace` with a real file `TraceListener`, query strings redacted everywhere.

**Dependency closure the deploy script must enumerate.** With `CopyLocalLockFileAssemblies=true`, an ordinary build leaves `SolidGround.Revit.dll`, `SolidGround.Core.dll`, `NetTopologySuite.dll`, and `ProjNET.dll` flat in `bin/Release/net10.0-windows/` (item 5). The deploy script's "fails closed on any missing file" check needs an independently derived expected set, either `SolidGround.Revit.deps.json` or the committed `packages.lock.json`, not a bare directory walk of `bin/`, which has no notion of what should be there. `RevitAPI.dll`/`RevitAPIUI.dll` must never appear in the deployed folder; that specific check needs no expected set, since their expected count is always zero. The script must also create the missing `%APPDATA%\Autodesk\Revit\Addins\2027` leaf directory itself, since only that leaf, not its `Addins` parent, is confirmed absent on a fresh machine (item 3).
