# OpenTopography USGS 1 m source

Issue #4 implements the first `IElevationSource`: `SolidGround.Core.Sources.OpenTopography.OpenTopographyUsgs1mSource`, which calls OpenTopography's `usgsdem` endpoint for the `USGS1m` dataset as an `AAIGrid` response. It adds no package reference; it uses only `System.Net.Http`, `System.IO.Compression`, `System.Xml.Linq`, and `System.Text`.

## Endpoint contract, verified 2026-09-15/16

Checked against the [OpenTopography OpenAPI definition](https://portal.opentopography.org/apidocs/openapi.json) and [API documentation](https://portal.opentopography.org/apidocs/) on 2026-09-16:

- Endpoint: `GET https://portal.opentopography.org/API/usgsdem`.
- Query parameters: `datasetName` (enum `USGS30m`/`USGS10m`/`USGS1m`, required), `south`/`north` (`-90..90`), `west`/`east` (`-180..180`), `outputFormat` (enum `GTiff`/`AAIGrid`/`HFA`; the documented default is `GTiff`, so this source always sends `outputFormat=AAIGrid` explicitly), and `API_Key` (required, a **query parameter** named exactly `API_Key` — the API has no header transport for the key).
- Documented responses: `200 OK`, `204 No Data`, `400 Bad request`, `401 Unauthorized`, `500 Internal error`. The OpenAPI definition does not document `403` or `429`, and does not document response content types.
- USGS1m carries a documented 250 km² per-request area limit and undocumented rate limits (200 calls/24h for academic accounts, 50/24h otherwise; no documented HTTP shape for exceeding them). USGS 1 m access itself is restricted to academic users or an enterprise API key.
- Observed live with an invalid key: HTTP 401, `Content-Type: application/xml`, body exactly `<?xml version="1.0" encoding="UTF-8" standalone="yes"?><error>Error: Not a valid format API Key: invalid. Please register for an API key at www.opentopography.org</error>`. The server echoes the submitted key back into the body, which is why every server-supplied message this source surfaces is redacted before it reaches an exception.

## Key transport and redaction

Because `API_Key` is a query parameter, the raw key value necessarily appears in the outgoing request URI. `OpenTopographyApiKey` wraps the raw string, exposes it only through an `internal` accessor the request builder uses, and its `ToString()` and `[DebuggerDisplay]` both read `[REDACTED]`. No public member of `SolidGround.Core` returns the raw value; an acquisition makes either one HTTP call (when the data response already carries its own reference metadata) or two (the identical request repeated with `outputFormat=GTiff`, when it does not — see "Two-request contract, verified 2026-09-19" below), and the key is used solely to build those request URI(s).

Every URI this source surfaces outside the outgoing request(s) themselves — in an exception property, a log-worthy string, or a report — is passed through `OpenTopographyRedaction.RedactUri`, which replaces the value of any `API_Key` query parameter (any position, case-insensitive, even with a missing value) with `REDACTED`. Any server-supplied text (an error body, an `HttpRequestException.Message`, and so on) is passed through `OpenTopographyRedaction.RedactText`, which removes the raw key value, its `Uri.EscapeDataString` form, and any literal `API_Key=<value>` pattern (independent of whether a key is even available), replacing each with `[REDACTED]`, then bounds the result to 512 characters. `OpenTopographyException.RedactedRequestUri` is therefore the only request-URI form this source ever exposes, and every exception's `ServerMessage` (where present) is pre-redacted and has its XML/HTML tags stripped.

`Exception.ToString()` recurses into `InnerException`, so an exception's own outer `Message` being redacted is not enough: `AcquireDetailedAsync`'s `HttpRequestException`/`IOException`/timeout-style `OperationCanceledException` catches never attach the original caught exception as `OpenTopographyNetworkException`'s `InnerException` (its `Message` could itself embed the request URI, for example from a caller-attached `DelegatingHandler`). Each instead redacts that exception's `Message` first and rebuilds a new exception of the same runtime type from the redacted text, the same pattern the WKT-parsing catches below already use for `FormatException`/`ArgumentException`.

Every message states what was observed (status code, content type, entry names, or the redacted server text) and what the caller can do next. This source never retries with a different dataset or output format and never sends more than two HTTP requests per call — the data request and, only when it carries no reference metadata of its own, the metadata request — on any path, success or failure.

### Response body truncation

`ReadBodyAsync` never throws when a response body exceeds `MaximumResponseBytes`; it returns `(Body, Truncated)` and leaves the decision to its caller, which already knows the response's HTTP status code:

- For a **200 (OK)** response, a truncated body is never parsed as a zip or bare AAIGrid; `HandleSuccessAsync` throws `OpenTopographyUnexpectedResponseException` directly, with no body-derived text in the message.
- For every **documented non-200 status** (401, 403, 429, 400, 5xx), a truncated body does not change which exception type is thrown: the status code is classified exactly as it would be for a complete body, and a fixed note — "(response truncated after it exceeded the configured `<n>` byte limit)" — is appended after the redacted, tag-stripped, bounded server text in `ServerMessage`.
- Only an **undocumented status code** with a truncated body falls through to `OpenTopographyUnexpectedResponseException`.

This keeps a status-appropriate exception (for example `OpenTopographyAuthorizationException` for a 401) from being pre-empted by a generic "unexpected response" purely because a caller-configured `MaximumResponseBytes` happened to be smaller than that response's error body.

Because a truncated body is always read as a byte-for-byte prefix of the real response, a chunk boundary can land in the middle of a key OpenTopography echoes back (see above): `OpenTopographyRedaction.RedactText`'s ordinary whole-value match cannot see a value that was cut in half, so when a non-200 body might be truncated, it additionally strips the longest trailing substring that matches a strict prefix of the key (or its escaped form) *after* applying the ordinary whole-value redaction, closing that gap without weakening redaction of a complete, untruncated body. Running the whole-value redaction first (rather than before, as an earlier revision did) matters for a key with a self-overlapping "border" — a proper suffix equal to a proper prefix, for example a key whose first and last characters match — because a complete, untruncated occurrence of such a key is now always removed as a whole before the trailing-fragment search can mistake its short border for the only surviving fragment. If the truncation cut lands inside a multi-byte UTF-8 character, `Encoding.UTF8.GetString` renders it as a single `U+FFFD` replacement character; the trailing-fragment search excludes a trailing `U+FFFD` from its comparison window (it cannot equal any character of the key) so the genuine key characters that decoded successfully immediately before it are still found and redacted.

## Coordinate reference identifiers that echo the API key

A `.prj`/`.aux.xml` sidecar is server-controlled text, and OpenTopography has been observed to echo a rejected key back in other response shapes (see above), so a WKT coordinate reference system name, datum name, or vertical datum name that unexpectedly equals or contains the configured API key is treated the same as any other untrustworthy echo, not as legitimate metadata. After `WellKnownTextReferenceParser.Parse` succeeds, `ParseZipResponse` checks `Horizontal.CoordinateReferenceSystem`, `Horizontal.Datum`, and `Vertical.Datum` against the key's raw and escaped forms and fails with `OpenTopographySourceMetadataException` (naming only the field, never the value) if any of them match. This runs before the parsed `WellKnownTextReference` can reach the returned `ElevationGrid`'s public `HorizontalReference`/`VerticalReference` — plain records with no `ToString()` override — so a matching value can never reach a caller through the successful, non-throwing acquisition path. It cannot reject legitimate data: a real coordinate reference system or datum name cannot coincidentally equal a random high-entropy API key.

## Two-request contract, verified 2026-09-19

Every request this source builds goes through `BuildRequestUri(box, apiKey, outputFormat)`; the data request always sends `outputFormat=AAIGrid` (`OpenTopographyUsgs1mSource.OutputFormat`). Live testing (see the Issue #10 update below) confirmed the data response never carries its own `.prj`/`.aux.xml` sidecar for USGS 1 m — it is always a bare `ncols`-prefixed AAIGrid text body. `HandleSuccessAsync` recognizes that shape (`FirstToken(text) == "ncols"`, case-insensitive) and hands it to `HandleBareAaiGridAsync` instead of failing immediately:

1. `AaiGridParser.ReadHeader` reads only the AAIGrid header (column/row counts, anchor, cell size, NODATA) from the already-received text; a malformed header fails with `OpenTopographySourceMetadataException` before any second request is sent.
2. A second `GET` is sent to `BuildRequestUri(box, apiKey, MetadataOutputFormat)` — the identical `datasetName`/`south`/`north`/`west`/`east` as the first request, with `outputFormat=GTiff` (`OpenTopographyUsgs1mSource.MetadataOutputFormat`) in place of `AAIGrid` — through the same `SendGetAsync` helper the first request uses, with `HttpCompletionOption.ResponseHeadersRead` and the identical `MaximumResponseBytes` cap. A non-200 metadata response is classified by the same `ClassifyNonSuccessResponseAsync` helper the data request uses, so a 204/400/401/403/429/5xx/undocumented-status metadata response raises the identical exception type as the equivalent data-response status, carrying the metadata request's own redacted URI; a timeout or transport failure on this request raises `OpenTopographyNetworkException` exactly as it would for the first.
3. The metadata response body must begin with a recognized TIFF byte-order mark and classic-TIFF magic number — `49 49 2A 00` ("II*\0", little-endian) or `4D 4D 00 2A` ("MM\0*", big-endian) — or `OpenTopographyUnexpectedResponseException` fires immediately, with no attempt to parse it as anything else.
4. `GeoTiffMetadataReader.Read` parses only IFD0's tag directory and, when present, the GeoKey directory (tag 34735) plus its GeoAsciiParams (34737) and GeoDoubleParams (34736) resolution tags — never a pixel, never a decompression step — and rejects BigTIFF (magic 43) outright. Every offset and count it follows is bounds-checked against the buffer, so a truncated or malicious buffer fails with `FormatException` (wrapped as `OpenTopographySourceMetadataException`), never a raw indexing exception.
5. `ValidateGeoTiffMetadata` then requires: GeoKey 1024 (`GTModelTypeGeoKey`) equals 1 (projected); GeoKey 3072 (`ProjectedCSTypeGeoKey`) is present and accepted by `NorthAmericanUtmWellKnownText.IsSupported` (the 40 verified NAD83-family UTM zone codes — see "GeoKey to WKT synthesis" below); for zone 19N specifically (the one supported zone that also reaches Puerto Rico), the request's own bounding box is not entirely south of `OpenTopographyUsgs1mSource.MinimumConusLatitudeForZone19N` (24.5 degrees north, south of the Florida Keys — see "CONUS scope and its rationale" below); GeoKey 3076 (`ProjLinearUnitsGeoKey`) is absent or exactly 9001 (metre); GeoKey 1025 (`GTRasterTypeGeoKey`) is 1 (PixelIsArea) or 2 (PixelIsPoint); tag 33550 (`ModelPixelScaleTag`) is present; tag 33922 (`ModelTiepointTag`) is present; and tag 42113 (`GDAL_NODATA`) is present and parses as an invariant-culture `double`. Each failure raises `OpenTopographySourceMetadataException` naming the specific GeoKey or tag and its observed (redacted) value — never a silent default. The unsupported-projected-code check is the one exception: it names only the observed EPSG code (for example `EPSG:26901`), not GeoKey 3072 (`ProjectedCSTypeGeoKey`) by number, because that message is aimed at an operator choosing a supported zone rather than someone debugging raw GeoKeys.
6. `EnsureGridsAgree` then verifies the AAIGrid header and the GeoTIFF metadata describe the identical grid, using exact `double` equality everywhere except the corner comparison, which allows `OpenTopographyUsgs1mSource.GridAgreementTolerance` (`1e-6`, in the raster's own horizontal units): `ImageWidth`/`ImageLength` against `ncols`/`nrows`; `ModelPixelScale`'s X and Y against `cellsize`; and the GeoTIFF's derived lower-left corner against the AAIGrid header's own lower-left corner. The GeoTIFF's upper-left corner is `(tiepointX - tiepointI*scaleX, tiepointY + tiepointJ*scaleY)` for `GTRasterTypeGeoKey` 1 (PixelIsArea), or that point shifted by half a cell in each axis — `(... - scaleX/2, ... + scaleY/2)` — for PixelIsPoint (2); its lower-left corner subtracts `ImageLength * scaleY` from the upper-left Y (the X coordinate is unchanged). The AAIGrid side's own lower-left corner is its header anchor directly for a corner-anchored grid, or the anchor shifted by half a cell toward the grid's true lower-left corner for a center-anchored one. Finally, the GeoTIFF's `GDAL_NODATA` value must equal the AAIGrid header's own `NODATA_value` exactly. Any disagreement raises `OpenTopographySourceMetadataException` naming the disagreeing field and both observed values.
7. GeoKey 1026 (`GTCitationGeoKey`), 2049 (`GeogCitationGeoKey`), and 3073 (`PCSCitationGeoKey`), when present, are all passed through the same API-key-echo check ("Coordinate reference identifiers that echo the API key" above), and `GDAL_NODATA`'s own text is bounded by the same `OpenTopographyRedaction.RedactText` every other server-supplied string on this source already receives, before any of them can reach an exception message or the evidence record.
8. The horizontal reference is synthesized as WKT from the GeoKeys' EPSG code (see "GeoKey to WKT synthesis" below) and parsed with the same `WellKnownTextReferenceParser.Parse` every other path uses; the original AAIGrid text is then parsed with `AaiGridParser.Parse` using that parsed reference — the metadata response's own bytes are never parsed for anything beyond its directory.

A successful hybrid acquisition's `OpenTopographyResponseEvidence.MetadataRequest` is a non-null `OpenTopographyMetadataRequestEvidence` carrying the metadata request's own redacted URI, status code, content type, content-disposition file name, response byte count, the GeoKeys' EPSG code, redacted citation, `"PixelIsArea"`/`"PixelIsPoint"`, and image width/height; `ReferenceSource` is `GeoTiffGeoKeys`; `HorizontalReferenceOrigin` is `SourceMetadataResponse`; `VerticalReferenceOrigin` is `DatasetDocumentation` (see "Declared vertical reference" below). A single-request, zip-sidecar acquisition still sets `MetadataRequest` to `null` and both origins to `SourceResponse`.

Because a bare AAIGrid data response now costs a second request before it can succeed, such an acquisition costs two calls against the configured API key's daily quota, not one; a response that already carries its own `.prj`/`.aux.xml` sidecar still costs only one. The CLI's `--timeout` (`docs/architecture/cli-workflow.md`'s "Options and defaults" section) sets the same `HttpClient.Timeout` applied to both requests independently, so a hybrid acquisition's two sequential requests may each take up to the configured timeout before the overall acquisition fails or succeeds.

**Update, Issue #23 (2026-09-20): a minimum-area probe and automatic padding, upstream of both requests.** Both requests this two-request contract sends carry whichever box `SolidGround.Core.Aois.AoiNormalizer.Normalize` produced, and that box is now, by default, never smaller than 110 m per side: a live probe at (withheld) found a 100 m square (0.01 km²) rejected with HTTP 400, `Error: The selected area is too small: 0.01 km2`, while a 100.5 m square (0.01010025 km²), 101 m, 105 m, and 120 m squares were all accepted. `AoiNormalizationOptions.MinimumFetchEnvelopeSide` (default `LinearDistance.Meters(110d)`, a 21 percent margin over the observed 0.01 km² floor) widens a too-small envelope symmetrically about its own center before either the `AAIGrid` or the `GTiff` request is built, so both requests in this two-request contract already carry the padded box — there is no separate padding step between them. See `docs/architecture/aoi-normalization-and-clipping.md`'s "Minimum fetch envelope, verified 2026-09-20" section for the full rule, factors, and the single-location caveat on that probe; `ApproximateAreaSquareKilometers`'s own 250 km² maximum check (above) is unaffected — this is a floor, not a ceiling, and the two checks remain independent.

## GeoKey to WKT synthesis

`SolidGround.Core.Sources.OpenTopography.NorthAmericanUtmWellKnownText` synthesizes the WKT1 `COMPD_CS` text for the EPSG projected coordinate system code the GeoTIFF GeoKeys reported (GeoKey 3072), paired with the declared vertical reference (see "Declared vertical reference" below), without adding any general-purpose WKT-generation library. `IsSupported(epsgCode)` accepts exactly the 40 codes in `NorthAmericanUtmWellKnownText.Definitions`: UTM zones 10N through 19N under four verified NAD83 realizations — NAD83 (EPSG 26910-26919, geographic base EPSG:4269), NAD83(HARN) (EPSG 3740-3749, geographic base EPSG:4152), NAD83(NSRS2007) (EPSG 3717-3726, geographic base EPSG:4759), and NAD83(2011) (EPSG 6339-6348, geographic base EPSG:6318) — with each zone's `centralMeridian = 6 * zone - 183`. Zones 10N-18N lie entirely within the conterminous United States; zone 19N also reaches Puerto Rico, so `OpenTopographyUsgs1mSource.ValidateGeoTiffMetadata` separately rejects a zone 19N result whose request bounding box lies entirely south of `MinimumConusLatitudeForZone19N` (24.5 degrees north, south of the Florida Keys) rather than assume the declared NAVD88 reference applies there — see "CONUS scope and its rationale" below. An unsupported code — any EPSG family other than these four realizations, or one of their own zones outside 10N-19N, for example NAD83's own zone 1N (Alaska) — is never guessed at: `ValidateGeoTiffMetadata` rejects it with `OpenTopographySourceMetadataException` naming the observed code before `Create` is ever called, and `Create`/`ZoneOf` themselves throw `ArgumentOutOfRangeException` for the same input if called directly.

`Create(epsgCode, vertical)` builds the WKT from a fixed set of literal template lines — the same ESRI-style dialect the committed `tests/SolidGround.Tests/Fixtures/example-site-synthetic.prj` fixture already uses, and byte-identical to that fixture for zone 15 under plain NAD83 (EPSG:26915). This is deliberately WKT1, not WKT2, and deliberately this ESRI-style dialect rather than the OGC WKT `epsg.io` itself serves: `ProjNetHorizontalCoordinateTransformFactory.Create` (`docs/architecture/coordinate-transformation-and-units.md`'s "The ProjNET adapter" section) needs WKT1 because the pinned ProjNET 2.1.0 rejects WKT2 keywords structurally, and the synthesized text is fed to that same factory as the target WKT, byte for byte, so it must already be in the one dialect both `WellKnownTextReferenceParser` and ProjNET's own `CreateFromWkt` accept for a compound CRS — see that design note's "The WKT flow" section. The matched `NorthAmericanUtmDefinition`'s `ProjectedName` is interpolated at both the `COMPD_CS` name's prefix and the `PROJCS` name itself; its `GeographicName` and `DatumName` are interpolated once each, into the `GEOGCS` and `DATUM` names; the zone's derived central meridian and the EPSG code are each interpolated once, rendered with `CultureInfo.InvariantCulture` (the central meridian as `"{value}.0"`). The vertical (`VERT_CS`) portion additionally interpolates the declared vertical datum name — used three times, in the `COMPD_CS` name, the `VERT_CS` name, and the `VERT_DATUM` name — and a fixed per-unit literal selected by `vertical.Unit` (one of three literal strings, never computed); see "Declared vertical reference" below for what supplies that datum name today. Every other token, including every other numeric literal (`6378137.0`, `298.257222101`, `500000.0`, `0.9996`, and so on) and the `GEOGCS`'s lack of its own `AUTHORITY` child, is copied verbatim from the fixture, so no floating-point formatting decision can ever change the synthesized text and zone 15's byte-identical output under plain NAD83 is preserved unchanged by the four-realization table.

Zone 15's central meridian is `6 * 15 - 183 = -93`, matching the [EPSG:26915 definition](https://epsg.io/26915) (read 2026-09-19): `PROJECTION["Transverse_Mercator"]` with `latitude_of_origin 0`, `central_meridian -93`, `scale_factor 0.9996`, `false_easting 500000`, `false_northing 0`, the GRS 1980 spheroid (`6378137`, `298.257222101`), over `GEOGCS["NAD83", ...]`, authority `EPSG:26915`; every one of those parameters appears in `Create`'s fixed template as the literal matching this citation. The vertical half of the `COMPD_CS` is built the same way, from a fixed per-unit literal rather than a computed one; see "Declared vertical reference" for what fills it.

**Naming choice.** `ProjectedName`, `GeographicName`, and `DatumName` use the ESRI-style underscored names `Create`'s fixed template already used for plain NAD83 (`"NAD_1983_UTM_Zone_15N"`, `"GCS_North_American_1983"`, `"NAD83"`), not epsg.io's own slash-delimited `Name` column (`"NAD83 / UTM zone 15N"`) — the template's dialect predates this issue and byte-identical fixture output for 26915 depends on keeping it. The other three realizations follow the same pattern (`"NAD_1983_HARN_UTM_Zone_15N"`, `"GCS_North_American_1983_HARN"`, `"NAD83(HARN)"`, and so on), including keeping each realization's parenthesized short name — `"NAD83(HARN)"`, `"NAD83(NSRS2007)"`, `"NAD83(2011)"` — as the literal `DATUM` name rather than substituting an underscore (`"NAD83_HARN"`): a dedicated test (`NorthAmericanUtmWellKnownTextTests.EveryDefinitionBuildsAProjNetTransformThatMapsItsCentralMeridianToFalseEasting`) proved the pinned ProjNET 2.1.0 accepts a quoted `DATUM` name containing parentheses through `ProjNetHorizontalCoordinateTransformFactory.Create` before this choice was made, so the underscore-style fallback the design considered was never needed.

**CONUS scope and its rationale.** SolidGround verified and tabulated only zones 10N-19N for these four realizations, not every zone EPSG registers for them (NAD83 alone registers zones 1N-23N). The declared NAVD88 vertical reference this source pairs with every synthesized horizontal reference (see "Declared vertical reference" below) is documented by USGS for the conterminous United States; Alaska, Hawaii, Puerto Rico, the Virgin Islands, and the territories use per-project or local vertical datums instead, per the USGS Lidar Base Specification and FAQ. EPSG:5703 (NAVD88 height)'s own area of use happens to name Alaska alongside CONUS, but that alone does not establish which vertical datum the USGS 1 m *product* actually uses for an Alaska tile — USGS's own specification says the datum for Alaska (and Hawaii, Puerto Rico, the Virgin Islands, and other territories) is agreed per project, not fixed by the national specification the CONUS tiles follow. Extending `NorthAmericanUtmWellKnownText` to a non-CONUS zone would therefore pair a horizontal reference this source *can* verify with a vertical reference it cannot, so those zones fail rather than assume, exactly like an unrecognized EPSG family. Zone 19N is the one exception to a clean per-zone CONUS/non-CONUS split: EPSG 26919/3749/3726/6348 also cover Puerto Rico (roughly 17.9-18.5 degrees north), not only the conterminous United States latitudes (for example Maine) the same zone reaches, so `NorthAmericanUtmWellKnownText` cannot itself tell the two apart from the EPSG code alone; `OpenTopographyUsgs1mSource.ValidateGeoTiffMetadata` closes that gap using the request's own bounding box latitude (see "Declared vertical reference" below).

## Declared vertical reference

Neither the AAIGrid data response nor the GeoTIFF metadata response OpenTopography returns for a USGS 1 m request carries any vertical GeoKey: the observed live GeoKey directory carries only GeoKeys 1024, 1025, 1026, 2049, 2054, 3072, and 3076 — no GeoKey 4096 (`VerticalCSTypeGeoKey`) or its siblings. SolidGround therefore never reads a vertical reference off either response; instead, `OpenTopographyUsgs1mSourceOptions.DeclaredVerticalReference` (default `new VerticalReference("NAVD88", LengthUnit.Meter)`, geoid model deliberately `null`) declares one from the dataset's own published documentation, applying this source's "fail rather than assume" posture to a total absence of vertical metadata rather than to a disagreement.

The declared value is sourced from OpenTopography's [USGS 1 m dataset page](https://portal.opentopography.org/raster?opentopoID=OTNED.012021.4269.3) (read 2026-09-19), which states: "All bare earth elevation values are in meters and are referenced to the North American Vertical Datum of 1988 (NAVD88)." NAVD88 height in metres is [EPSG:5703](https://epsg.io/5703); SolidGround's `VerticalReference` model carries a datum name, a unit, and an optional geoid model string rather than a numeric EPSG code, but the declared datum name `"NAVD88"` and `LengthUnit.Meter` are exactly EPSG:5703's own datum and unit. The geoid model is deliberately left `null`: the dataset page names the vertical datum and its unit but not a specific geoid model (for example Geoid12B), and SolidGround does not fabricate one it was not told.

Every reference this section covers is recorded with `ReferenceOrigin.DatasetDocumentation` — never `SourceResponse` or `SourceMetadataResponse` — in `OpenTopographyResponseEvidence.VerticalReferenceOrigin`, the `.source.json` sidecar's `verticalReferenceOrigin`, and the export document's `provenance.sourceVerticalReferenceOrigin` (`docs/architecture/provenance-and-deterministic-exports.md`'s "Export document manifest, schema version 2" section), so a reader can always tell that this value came from documentation SolidGround declared rather than from anything either OpenTopography response actually returned.

**Update, Issue #22 (2026-09-20): why the declared vertical reference, and support, stop at the CONUS zones.** USGS's [Lidar Base Specification](https://www.usgs.gov/ngp-standards-and-specifications/lidar-base-specification-data-processing-and-handling-requirements) (read 2026-09-20) states, for the conterminous United States: "The horizontal datum for latitude and longitude and ellipsoid heights will be the North American Datum of 1983 (NAD 83) using the most recent NGS-published adjustment (currently NAD 83, epoch 2010.00, realization of 2011)" and "The vertical datum for orthometric heights will be the North American Vertical Datum of 1988 (NAVD 88)." NAVD88 height in metres is [EPSG:5703](https://epsg.io/5703) (read 2026-09-20), whose own area of use lists "Mexico - onshore. United States (USA) - CONUS and Alaska - onshore" — Alaska included. The same specification, for "Alaska, American Samoa, Commonwealth of the Northern Mariana Islands, Guam, Hawaii, Puerto Rico, U.S. Virgin Islands, and other areas," instead says: "USGS–NGP and all collection partners shall agree to and specify horizontal and vertical datums, ellipsoids, and geoids in advance of data collection" — a per-project agreement, not one fixed national datum. The USGS [DEM FAQ](https://www.usgs.gov/faqs/what-projection-horizontal-datum-vertical-datum-and-resolution-a-usgs-digital-elevation-model) (read 2026-09-20) is consistent with this: "Typically the North American Vertical Datum of 1988 (NAVD88) ... For Hawaii, Puerto Rico, U.S. Virgin Islands, and Pacific Island territories, the vertical datum is typically referenced to local mean sea level" — naming no EPSG-registered code for those territories at all. Puerto Rico and the U.S. Virgin Islands do each have a registered vertical CRS — [EPSG:6641](https://epsg.io/6641) (PRVD02 height) and [EPSG:6642](https://epsg.io/6642) (VIVD09 height), both read 2026-09-20 — but SolidGround has not verified that the USGS 1 m product actually uses either one for those territories' tiles, so neither is wired into `OpenTopographyUsgs1mSourceOptions.DeclaredVerticalReference` today. Hawaii has no dedicated EPSG vertical CRS to fall back to at all: EPSG's only generic candidate, EPSG:5714 ("MSL height", area of use World), carries its own warning against exactly this use ("Users are advised to not use this generic CRS but instead use one with a specific datum origin"), so a Hawaii tile's vertical reference is undeclared in SolidGround's own terms, not merely unverified. Because EPSG:5703's area of use naming Alaska does not by itself establish that the 1 m *product* uses NAVD88 there — the Lidar Base Specification's own per-project clause governs Alaska, exactly like Hawaii, Puerto Rico, and the Virgin Islands — `NorthAmericanUtmWellKnownText` supports only ten UTM zones (10N-19N), nine of which (10N-18N) lie entirely within the conterminous United States, where the declared NAVD88 reference is unambiguous. The tenth, zone 19N, also reaches Puerto Rico, where that same per-project clause applies instead of the fixed CONUS requirement, so `OpenTopographyUsgs1mSource.ValidateGeoTiffMetadata` additionally rejects a zone 19N result whose request bounding box lies entirely south of `MinimumConusLatitudeForZone19N` (24.5 degrees north) rather than assume the fixed NAVD88 requirement extends there. Every other zone or family still fails rather than assume, exactly as before (see "GeoKey to WKT synthesis" above).

## "Fail rather than assume" metadata policy

AGENTS.md forbids assuming the USGS 1 m mosaic uses the projected CRS and vertical datum documented for the underlying point-cloud collection it was derived from. This source therefore never supplies a default horizontal or vertical reference. It reads whatever reference metadata the response actually carries — a `.prj` sidecar's WKT, or an `.aux.xml` sidecar's `<SRS>` element — parses it with the new generic `SolidGround.Core.Metadata.WellKnownTextReferenceParser`, and fails with `OpenTopographySourceMetadataException` when no usable metadata is present, when the WKT does not parse, or when it describes no vertical coordinate system.

**Open question the live test must answer:** the OpenAPI definition and API documentation do not state whether an `AAIGrid` response body is a bare `.asc` text stream or a zip archive containing `.asc` plus a `.prj` (or `.aux.xml`) sidecar, nor what reference metadata (if any) it carries. This source handles both packagings it can conceive of — bare text (which fails, because bare AAIGrid has no reference metadata section) and a zip with a `.prj` or `.aux.xml` sidecar (which succeeds) — but only a real, opted-in call to the live endpoint (see below) can confirm which packaging OpenTopography actually returns for `USGS1m`/`AAIGrid`, and what its sidecar actually contains. Until that test is run against a real account, this remains an open question; if the live packaging differs from both handled shapes, this design note and the source will need a follow-up revision.

**Update, Issue #10 (2026-09-19):** the live endpoint confirms the first of the two packagings this note anticipated above — bare text, which fails — rather than an unanticipated third shape: every request aimed at a real-coverage USGS 1 m area returned a bare, unzipped `.asc` body with no `.prj`/`.aux.xml` sidecar and no reference metadata of any kind. This source's existing "fail rather than assume" design already handles it correctly — `HandleSuccessAsync` throws `OpenTopographySourceMetadataException` rather than guessing a CRS — and the CLI surfaces that as exit code 4 (`source-quality`) on every `fetch`/`run` attempted against a real-coverage area large enough to clear OpenTopography's own undocumented per-request area minimum, with no fallback to a coarser dataset or an assumed reference; a request whose area falls below that minimum instead fails earlier, at HTTP 400 with exit code 2 (usage), before any raster is returned. A same-request `GTiff` capture over the identical box carries the horizontal reference the `AAIGrid` body omits (`ProjectedCSTypeGeoKey` 26915, "NAD83 / UTM zone 15N") but still no vertical GeoKeys, and OpenTopography also rejects a request below an empirically observed area threshold (a 100 m square was rejected, a 120 m square was accepted) that neither the OpenAPI definition nor the dataset documentation states. See "Response packaging and metadata observed" and "Source packaging decision for the owner" in `docs/architecture/phase-1-validation.md` for the full evidence and the resulting options recorded for the owner's decision.

**Update, Issue #21 (2026-09-19):** the two-request GeoTIFF-GeoKeys hybrid flow that resolves the bare-AAIGrid packaging this update describes is implemented and documented in "Two-request contract, verified 2026-09-19", "GeoKey to WKT synthesis", and "Declared vertical reference" above.

**Update, Issue #21 (2026-09-19):** a bare AAIGrid response for a supported NAD83 UTM zone (EPSG 26901-26923, as this source recognized them on 2026-09-19) no longer ends a real-coverage `fetch`/`run` in exit code 4: `HandleBareAaiGridAsync` now completes the acquisition by recovering the horizontal reference from a second GeoTIFF-GeoKeys request and declaring the vertical reference from dataset documentation (see the three sections above). Exit code 4 (`source-quality`, via `OpenTopographySourceMetadataException`/`OpenTopographyUnexpectedResponseException`/`OpenTopographyNetworkException`) still results from: an unsupported projected coordinate system code (any EPSG family or zone this source has not verified — see "GeoKey to WKT synthesis" below for what changed here on 2026-09-20); a missing or invalid required GeoKey or tag (model type, linear units, raster type, pixel scale, tiepoint, or `GDAL_NODATA`); the two responses describing grids that disagree beyond `GridAgreementTolerance`; a metadata response that is not GeoTIFF or exceeds `MaximumResponseBytes`; a citation that echoes the configured API key; or any of the pre-existing single-request failure causes this section and the failure taxonomy above already document. A NAD83(2011) UTM zone in 10N-19N (for example EPSG:6344, zone 15N), which the paragraph above listed as an example of a code that still failed, now succeeds.

## Contract adjustment (deliverable A)

`ElevationSourceMetadata.CollectionPeriod` and `QualityLevel` are now `CollectionPeriod?` and `string?`, defaulting to `null`. The `usgsdem` response carries neither a collection period nor a catalog quality level, and fabricating catalog values (for example, borrowing the point-cloud collection's 2017-02-17..2017-02-27 dates) would violate the same "fail rather than assume" rule. A supplied, non-null `QualityLevel` that is blank or whitespace-only is still rejected. `OpenTopographyUsgs1mSource` always builds `ElevationSourceMetadata("OpenTopography", "USGS1m", null, null)`.

## User secrets deferral

.NET user secrets is a host/CLI concern: it needs a package reference (`Microsoft.Extensions.Configuration.UserSecrets`) and a configured `UserSecretsId`, neither of which belongs in the Revit-free, package-free Core assembly. `IOpenTopographyApiKeyProvider` keeps key resolution pluggable; Core supplies only `EnvironmentOpenTopographyApiKeyProvider` (reads `OPENTOPOGRAPHY_API_KEY`, trimmed, empty treated as absent) and `StaticOpenTopographyApiKeyProvider` (fixed value, for tests and hosts with their own configuration). Reading the key from user secrets is deferred to the CLI issue, which can compose its own provider over `Microsoft.Extensions.Configuration`.

## Running the live test

An opt-in live test (in a separate file, not part of the default offline suite) calls the real endpoint for a small bounding box around the example-site scenario (`41.591194, -93.603806`, roughly ±0.0007°) and asserts a successful acquisition. It never prints the key or the request URI. It skips (via `Assert.Skip`) unless **both**:

- the environment variable `SOLIDGROUND_OPENTOPOGRAPHY_LIVE` is exactly `"1"`, and
- `OPENTOPOGRAPHY_API_KEY` is set to a non-empty value.

Example (PowerShell, from the repository root):

```powershell
$env:SOLIDGROUND_OPENTOPOGRAPHY_LIVE = "1"
$env:OPENTOPOGRAPHY_API_KEY = "<your key>"
dotnet test --project tests/SolidGround.Tests/SolidGround.Tests.csproj --configuration Release
```

USGS 1 m access requires academic authorization or an enterprise API key; without one, the live test will observe `OpenTopographyAuthorizationException` rather than a successful acquisition even with the opt-in flag set. Do not set `SOLIDGROUND_OPENTOPOGRAPHY_LIVE` or export a real key in CI; the self-hosted workflow runs only the default offline suite.

**Update, Issue #10 (2026-09-19):** with a valid key and the opt-in flag both set, this test currently fails with `OpenTopographySourceMetadataException` rather than passing, for the bare-AAIGrid packaging reason recorded above.

**Update, Issue #21 (2026-09-19):** with a valid key and the opt-in flag both set, this test now passes rather than failing — the opted-in suite reported `total: 706 / failed: 0 / succeeded: 706 / skipped: 0`. It issues two live requests (the `AAIGrid` data request and the `GTiff` metadata request the hybrid flow in "Two-request contract, verified 2026-09-19" adds) and asserts: `Evidence.ReferenceSource` is `GeoTiffGeoKeys`; `Evidence.HorizontalReferenceOrigin` is `SourceMetadataResponse` and `Evidence.VerticalReferenceOrigin` is `DatasetDocumentation`; the metadata request's own `ProjectedCoordinateSystemCode` is `26915`; the acquired data's `HorizontalReference` is `EPSG:26915`, projected, metre; its `VerticalReference` is `NAVD88`, metre; and the raw API key appears in neither the data request's nor the metadata request's own redacted URI.
