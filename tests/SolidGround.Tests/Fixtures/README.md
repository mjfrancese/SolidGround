# Offline fixtures

`example-site-synthetic.asc` is a deliberately small synthetic AAIGrid near the projected coordinates of the example-site test scenario. Its elevations are illustrative parser inputs, not measured terrain and not an OpenTopography response. The fixture contains one explicit NODATA cell and no request URL, authorization header, or API credential.

`example-site-synthetic.prj` is a hand-written, ESRI-style `COMPD_CS` Well-Known Text definition (NAD83 / UTM zone 15N, `AUTHORITY["EPSG","26915"]`, with a `VERT_CS` NAVD88 height in meters) sized to match `example-site-synthetic.asc`. It is illustrative WKT for parser and OpenTopography-source tests, not a real OpenTopography sidecar response, and contains no request URL, authorization header, or API credential. Tests build zip archives in memory from these two files; no zip is committed.

`example-site-synthetic-parcel.geojson` and `example-site-synthetic-parcel.wkt` are the same synthetic lot boundary — a 1,600 m² (~17,222.26 sq ft) illustrative rectangle, not a real parcel survey — expressed in two independent reference forms for `ParcelGeometryParser` and AOI/clipping tests. The GeoJSON fixture is a `Feature` with a WGS 84 `Polygon` geometry centered on `41.591194, -93.603806`, with its half-width and half-height converted from meters to degrees using `Wgs84Ellipsoid`'s meters-per-degree factors at that latitude. The WKT fixture is a plain `POLYGON` in the same NAD83 / UTM zone 15N reference (`EPSG:26915`) `example-site-synthetic.prj` describes: a 40 m × 40 m square centered on easting/northing `449675.33`/`4604564.62`, the same point the GeoJSON fixture centers on. The example site sits only about 0.6° west of zone 15N's own `-93°` central meridian, which is why its easting (~449,675 m) sits just below the 500,000 m false easting rather than far above it (a site farther from the central meridian would show an easting well above 500000 m instead). Both are synthetic, illustrative boundaries, not a real parcel survey, and neither contains a request URL, authorization header, or API credential. Unlike an earlier version of this fixture pair, the WKT corners here are the literal forward-reprojection of the GeoJSON corners' implied square — an exact relationship, not merely the same nominal footprint — though no test relies on that exactness specifically, so either relationship would satisfy the existing coverage.

`example-site-synthetic.solidground.json` and `example-site-synthetic.points.csv` are the committed golden export bundle proving `TerrainExportBundleRenderer.Render` is byte-for-byte deterministic. `TerrainExportGoldenFileTests.GoldenPipelineRendersBytesIdenticalToTheCommittedGoldenFiles` produces them by a fixed, offline, platform-independent pipeline: parse `example-site-synthetic.prj` with `WellKnownTextReferenceParser.Parse`; parse `example-site-synthetic.asc` with `AaiGridParser.Parse` under that reference; build a `HorizontalTransformationDefinition` with `ProjNetHorizontalCoordinateTransformFactory.Create` (its WKT text and engine identity only — no coordinate is ever transformed by this pipeline, so no ProjNET or NetTopologySuite trigonometry can move a byte); clip the grid with a fixed, irregular, fractional-metre pentagon and a zero geometric buffer (`GridClipper` skips the NTS buffer call entirely for a zero buffer, so no trigonometry runs there either); snap a fixed candidate to a whole-number local origin with `LocalOriginSnapping` and build a `LocalCoordinateFrame` in `UsSurveyFoot`; simplify with `GridTerrainSimplifier` at a 500-point budget and `SimplificationMethod.CurvatureAware`; and render the result with `TerrainExportPayloadAssembler.Assemble` and `TerrainExportBundleRenderer.Render("example-site-synthetic")`. The clip pentagon deliberately covers the grid's NODATA cell (so the export still has to exclude it on elevation grounds, not merely a clip-boundary accident) while cutting off one corner cell outright (so the clip is not simply the whole grid). The same test file's other `[Fact]`s reuse this pipeline with a different output unit, a different snapped origin, and a real parcel-derived clip region (GeoJSON parcel → `AoiNormalizer` → forward reprojection → a buffered clip), asserting behavior rather than committing further golden bytes, because that path calls ProjNET's forward transform and an NTS geometric buffer and so is only proven deterministic within one process, not bit-for-bit across platforms.

**Update, SolidGround Issue #21 (2026-09-19):** `example-site-synthetic.solidground.json` is now a schema version 2 document (`TerrainProvenance.CurrentSchemaVersion`). Its `provenance` object carries two additional required fields, `sourceHorizontalReferenceOrigin` and `sourceVerticalReferenceOrigin`, immediately after `sourceVerticalReference` and before `localFrame`; the golden pipeline above passes `Operator`/`Operator` for both (the fixture's own `.prj`-derived reference is treated as an operator-supplied value in this offline pipeline, exactly as `process` labels its own horizontal reference). `example-site-synthetic.points.csv` is unchanged: the two new fields live only in the document, not the points file.

To regenerate these two files after an intentional format change: run `TerrainExportGoldenFileTests.GoldenPipelineRendersBytesIdenticalToTheCommittedGoldenFiles` once. A mismatch (or a missing golden) makes it write the freshly rendered bytes to a sibling `<file>.actual` path under the test output directory's own `Fixtures` copy (never under this source directory) and fail with that path and the first differing byte offset. Inspect the `.actual` file the same way `FixtureSecurityTests` inspects every committed fixture — no embedded request-URL scheme, API-key marker, or bearer/auth-header token, and no `0x0D` byte — copy it over the corresponding file in this directory, and rerun until the test passes. `.actual` files live only under `bin/` (already git-ignored) and are never committed.

Both golden files are LF-only: `.gitattributes` declares every file under `tests/SolidGround.Tests/Fixtures/**` as `text eol=lf` so a Windows checkout cannot reintroduce a `0x0D` byte the renderer never wrote, which would otherwise silently break the byte-for-byte comparison above on this workstation while passing on the Linux self-hosted CI runner (or vice versa). The pin covers every fixture, not just `*.json` and `*.csv`, because `example-site-synthetic.prj`'s WKT is embedded verbatim in the golden export: a CRLF checkout of the `.prj` file alone would change the exported bytes just as surely as a CRLF checkout of a golden file would.
