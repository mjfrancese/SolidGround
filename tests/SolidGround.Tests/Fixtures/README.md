# Offline fixtures

`robandee-synthetic.asc` is a deliberately small synthetic AAIGrid near the projected coordinates of the Robandee Lane test scenario. Its elevations are illustrative parser inputs, not measured terrain and not an OpenTopography response. The fixture contains one explicit NODATA cell and no request URL, authorization header, or API credential.

`robandee-synthetic.prj` is a hand-written, ESRI-style `COMPD_CS` Well-Known Text definition (NAD83 / UTM zone 15N, `AUTHORITY["EPSG","26915"]`, with a `VERT_CS` NAVD88 height in meters) sized to match `robandee-synthetic.asc`. It is illustrative WKT for parser and OpenTopography-source tests, not a real OpenTopography sidecar response, and contains no request URL, authorization header, or API credential. Tests build zip archives in memory from these two files; no zip is committed.

`robandee-synthetic-parcel.geojson` and `robandee-synthetic-parcel.wkt` are the same synthetic lot boundary — a ~1,346.72 m² (14,496 sq ft) rectangle, the Lot 191 footprint — expressed in two independent reference forms for `ParcelGeometryParser` and AOI/clipping tests. The GeoJSON fixture is a `Feature` with a WGS 84 `Polygon` geometry centered on `38.700186, -90.477652`, with its half-width and half-height converted from meters to degrees using `Wgs84Ellipsoid`'s meters-per-degree factors at that latitude. The WKT fixture is a plain `POLYGON` in the same NAD83 / UTM zone 15N reference (`EPSG:26915`) `robandee-synthetic.prj` describes, centered near easting/northing `719400`/`4286550` — close to `robandee-synthetic.asc`'s footprint, and the real UTM 15N easting for this longitude (Missouri sits roughly 2.5° east of zone 15's -93° central meridian, which is why an accurate easting here is near 719000 m, not the 500000 m false easting alone). Both are synthetic, illustrative boundaries, not a real parcel survey, and neither contains a request URL, authorization header, or API credential. Because the two fixtures use independent reference forms with no shared coordinate transform (Issue #6 owns that), they are not expected to be bit-for-bit reprojections of one another — only the same nominal footprint.

`robandee-synthetic.solidground.json` and `robandee-synthetic.points.csv` are the committed golden export bundle proving `TerrainExportBundleRenderer.Render` is byte-for-byte deterministic. `TerrainExportGoldenFileTests.GoldenPipelineRendersBytesIdenticalToTheCommittedGoldenFiles` produces them by a fixed, offline, platform-independent pipeline: parse `robandee-synthetic.prj` with `WellKnownTextReferenceParser.Parse`; parse `robandee-synthetic.asc` with `AaiGridParser.Parse` under that reference; build a `HorizontalTransformationDefinition` with `ProjNetHorizontalCoordinateTransformFactory.Create` (its WKT text and engine identity only — no coordinate is ever transformed by this pipeline, so no ProjNET or NetTopologySuite trigonometry can move a byte); clip the grid with a fixed, irregular, fractional-metre pentagon and a zero geometric buffer (`GridClipper` skips the NTS buffer call entirely for a zero buffer, so no trigonometry runs there either); snap a fixed candidate to a whole-number local origin with `LocalOriginSnapping` and build a `LocalCoordinateFrame` in `UsSurveyFoot`; simplify with `GridTerrainSimplifier` at a 500-point budget and `SimplificationMethod.CurvatureAware`; and render the result with `TerrainExportPayloadAssembler.Assemble` and `TerrainExportBundleRenderer.Render("robandee-synthetic")`. The clip pentagon deliberately covers the grid's NODATA cell (so the export still has to exclude it on elevation grounds, not merely a clip-boundary accident) while cutting off one corner cell outright (so the clip is not simply the whole grid). The same test file's other `[Fact]`s reuse this pipeline with a different output unit, a different snapped origin, and a real parcel-derived clip region (GeoJSON parcel → `AoiNormalizer` → forward reprojection → a buffered clip), asserting behavior rather than committing further golden bytes, because that path calls ProjNET's forward transform and an NTS geometric buffer and so is only proven deterministic within one process, not bit-for-bit across platforms.

To regenerate these two files after an intentional format change: run `TerrainExportGoldenFileTests.GoldenPipelineRendersBytesIdenticalToTheCommittedGoldenFiles` once. A mismatch (or a missing golden) makes it write the freshly rendered bytes to a sibling `<file>.actual` path under the test output directory's own `Fixtures` copy (never under this source directory) and fail with that path and the first differing byte offset. Inspect the `.actual` file the same way `FixtureSecurityTests` inspects every committed fixture — no embedded request-URL scheme, API-key marker, or bearer/auth-header token, and no `0x0D` byte — copy it over the corresponding file in this directory, and rerun until the test passes. `.actual` files live only under `bin/` (already git-ignored) and are never committed.

Both golden files are LF-only: `.gitattributes` declares `tests/SolidGround.Tests/Fixtures/*.json` and `*.csv` as `text eol=lf` so a Windows checkout cannot reintroduce a `0x0D` byte the renderer never wrote, which would otherwise silently break the byte-for-byte comparison above on this workstation while passing on the Linux `solidground-pve2` runner (or vice versa).
